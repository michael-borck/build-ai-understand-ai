# Preface 

## Why This Book Exists

You use LLM systems every day. You type into a chat box, upload a document and ask questions about it, watch a tool fetch a web page and reason over it. And if someone asked you what actually happened in there, you would probably say something vague about "the model". That vagueness has a cost: it is where confident nonsense gets past you.

The machinery is not that complicated. Strip away the dashboards and the marketing, and every LLM system in that first paragraph is one call to a model, wrapped in plain Python. A chatbot is that call plus a paragraph of instructions. A document question-answerer is that call plus a search. An agent is that call plus a loop that runs your functions. The package this book pairs with, `hands-on-ai`, makes each of those small enough to read in an afternoon, because when the whole thing fits in your head, the concept becomes visible.

A note on the title's word, since this book will spend eighteen chapters teaching you to check claims like it: AI is a wider field than this book. It includes search and symbolic reasoning, the classical machine learning of decision trees, support vector machines, and clustering that has filtered your spam and scored your transactions for decades, and the deep learning that produced both image classifiers and the large language models, LLMs, at this book's centre. Those older branches still run much of the world's consequential automation, often better than an LLM would. This book keeps the umbrella word for its title and earns it narrowly: Parts I to V are about LLM systems, and the optional Part VI opens with the older AI on its own terms before turning to the training loop itself. When any vendor, this book included, says "AI" without saying which branch, you will know to ask.

This book walks those builds in a deliberate order, in five parts that need nothing beyond a model you can call. You will write a little Python and read a little more. What you will not do in those five parts is train anything, install a framework, or take anyone's word for anything. An optional sixth part, clearly fenced, then opens the box a crack: it trains toy models in notebooks, at toy scale, for readers who want to see that side too. By the end, when a demo answers fluently, you will know which parts of what you saw were the model and which were a harness someone wrote on a Tuesday.

# One Call to the Model 

> Every AI system in this book starts the same way. Your program sends text to a model, and the model sends text back.

Package companion: the `chat` module of `hands-on-ai`. Listings in this chapter were checked against `hands-on-ai` 0.6.0.

Misconception this chapter kills: "AI is magic." It is one function call over HTTP.

The build: a five-line script that asks a question and prints the answer. Then the same call again, with the request it sends printed where you can read it.

Python you need: an import, a variable, a function call, and `print`.  teaches each of those. Read the code in this chapter even if you have not read the appendix yet. No listing is longer than a paragraph.

## The Concept First

When you type a question into a chat window and an answer appears, three ordinary things happen. The app takes your text and sends it across the network to a program running a model. The model produces reply text. The app receives that text and shows it to you.

The window, the typing indicator and the smooth scroll are presentation. Underneath them, text went out and text came back.

Once you see the event at that size, a useful question becomes available for every AI product you meet. What did this tool add around the plain call? A chat window adds an instruction at the front and keeps a transcript. A document helper adds a search before the call. An agent adds a loop after it. You will build each of those additions in later chapters. This chapter builds the call they all add to.

## Understanding Through Real Life

Think of posting a letter to a well-read stranger who answers questions by return mail.

Your envelope needs an address. In code, the address is a server URL, such as the Ollama server running on your own machine at `http://localhost:11434`. The envelope also needs a name, because one server can hold several models. The name is a string like `llama3`. Inside the envelope sits the letter itself. The letter is a short list of messages, and each message says who wrote it. One message carries your question.

The stranger reads the whole letter, writes a reply, and sends it back. Two details of the analogy matter later in this book. The stranger answers from what is in your letter and from what they learned long before you wrote. They have no other window into your life. And when the next letter arrives, they have forgotten yours completely, unless you copy the earlier exchange into the new letter. Part I takes those two details in turn.

## Connect a Model Before You Build

The build needs two things installed: the package, and a model it can reach. The free local path uses Ollama, which runs a model on your own machine and needs no account or API key.

```bash
pip install "hands-on-ai==0.6.0"
ollama pull llama3
handsonai doctor
The first command installs the version of the package this book is pinned to. The second downloads a small model. Downloading takes a few minutes the first time. The third command checks the whole path at once. It prints the server URL and model the package will use, and it tries to reach the server. Run it before you run any listing in this book. When something breaks in a later chapter, run it again first. Most first-week failures are a server that is not running or a model that was never downloaded, and `doctor` names both.

 covers the other routes: hosted providers, API keys, and the three environment variables that point the package at them. You do not need any of that yet.  explains why swapping providers later will change your settings and leave your code alone.

Read the line it prints before you change anything. "Could not connect" with a local address usually means Ollama is installed but not running yet. Start it, then run `handsonai doctor` again. A model name in the output that you never downloaded means the `ollama pull` step was skipped or used a different name.

## The Build: Five Lines

Make a new folder for this book's work and save this as `ask.py` inside it.

bash
python ask.py
The first run prints a short warm-up line while the model loads, then one sentence about a post office. Your sentence will differ from mine, and it will probably differ if you run the script twice. The model writes a fresh reply each time, so this book will not pretend that model output can be quoted word for word. Where output is shown in later chapters, it is one run's output, and yours should be similar in kind.

Read the listing line by line. The import line takes one function, `get_response`, out of the package's `chat` module and makes it available in your script. The blank line is for your eyes only. Python ignores it. The next line calls the function with one string, your question, and stores whatever comes back in a variable named `answer`. Nothing appears on screen yet. The last line prints the variable. If you delete it, the script will still make the call and still receive a reply. You will just never see the reply, and the run will look like it did nothing. Try that once.

The script contains no server address, no model name and no password. `get_response` found those in the package configuration, which `handsonai doctor` printed for you earlier. The defaults point at a local Ollama server. Settings live outside your code so that the code can stay this small.  opens that configuration up.

## Pull Back the Curtain: Print What You Sent

You still cannot see what left your machine, so print it. This script builds the request as data and shows it to you before anything is sent. It runs without a model, without a network, and it prints the same thing every time.

```python
# Listing 1.2 of 4: the request, as data (payload.py)
import json

model = "llama3"
messages = [
    {"role": "system", "content": "You are a helpful assistant."},
    {"role": "user", "content": "In one sentence, what does a post office do?"},
]
payload = {"model": model, "messages": messages}

print(json.dumps(payload, indent=2))

{
  "model": "llama3",
  "messages": [
    {
      "role": "system",
      "content": "You are a helpful assistant."
    },
    {
      "role": "user",
      "content": "In one sentence, what does a post office do?"
    }
  ]
}

This is the letter from the analogy, written as JSON. JSON is a text format for structured data, built from names, values, lists in square brackets, and groups in curly braces. You can read this one already. At the top level there are two names. `model` says which model should answer. `messages` holds a list of two messages, and each message is a group with a `role` and a `content`.

The `user` message is yours. It is the question you typed in Listing 1.1, unchanged. The `system` message above it is the interesting one. You did not write it. `get_response` put it there, because its default instruction to the model is the string "You are a helpful assistant." Every call in Listing 1.1 quietly sent two messages, and the first one was an instruction about how to behave.  is entirely about that first message, and about how much of a chatbot's apparent personality is one string in a list.

The list has room to grow. A conversation is this same list with more messages in it: your turns and the model's replies, in order, resent in full on every call.  shows why products built on this call go to that trouble.

## The Same Call Without the Package

`get_response` is a convenience. Real tools talk to models through a client library, and the package uses one too. Stripped of its retry and reporting code, the centre of `get_response` does this.

```python
# Listing 1.3 of 4: the call underneath, simplified from the package source
from openai import OpenAI

client = OpenAI(base_url="http://localhost:11434/v1", api_key="hands-on-ai")

response = client.chat.completions.create(
    model="llama3",
    messages=messages,
)

answer = response.choices[0].message.content
print(answer)
You do not need to run this. Read it for shape. A client is created with an address and a key. Local Ollama ignores the key, but the client insists on having one, so the package passes a placeholder. The `create` call takes the model name and the same `messages` list you printed in Listing 1.2. What comes back is a response object, and the reply text sits in one specific place inside it: the first choice, its message, its content. One line fishes the string out.

One more layer sits underneath the client. The client turns that call into an HTTP request: a `POST` to the address `http://localhost:11434/v1/chat/completions`, with your JSON payload as the body. The server answers with JSON, and the client tidies it into the response object. HTTP requests are how programs ask servers for things all over the web. Your browser made several hundred of them before breakfast. A model call is one of them, with a question in the body.

So what does the package add, if the bare call takes a dozen lines? Four things you have already benefited from without noticing. It reads the server, model and key from configuration instead of hard-coding them in your script. It supplies the default system message. It tries the call a second time if the first attempt fails. And it can keep a copy of each answer in a local cache, so a classroom can rerun a lesson and get the same replies.  explains the cache. They save you from typing the surrounds while you learn the middle.

Every chapter ends at a function like `get_response` and asks the same question. What does this add to the plain call? The package is small enough to answer that question by reading it. The source of `get_response` is one file, `chat/get_response.py`, in the package repository. Open it once this week. You will not understand every line yet. You will recognise the messages list and the `create` call, and that recognition is the point.

## What an Answer Costs

The server counts your text and the model's text in tokens. A token is a chunk of text, often a short word or part of a long one. Providers bill by tokens, and every model has a limit on how many tokens one call can carry. You do not need exact token arithmetic. You need the habit of looking at the count, because two later chapters turn on it: conversations get expensive as the resent list grows, and retrieval works by spending tokens on evidence.

Ask `get_response` to report the count.

```python
# Listing 1.4 of 4: the same call, with the receipt (ask_with_usage.py)
from hands_on_ai.chat import get_response

answer, usage = get_response(
    "In one sentence, what does a post office do?",
    return_usage=True,
)

print(answer)
print(usage)

With `return_usage=True`, the function hands back two values instead of one. Your script stores them in two variables. The second value is a small dictionary with three counts.

{'prompt_tokens': 31, 'completion_tokens': 22, 'total_tokens': 53}

Your numbers will differ a little, with the same shape. `prompt_tokens` counts everything you sent. That includes the system message you did not write, which is why a ten-word question costs more than ten tokens. `completion_tokens` counts the reply. `total_tokens` adds them.

Two ordinary situations return `None` instead of counts, so they do not look like bugs later. A streamed reply, printed piece by piece as it arrives, comes with no final count from most servers. And an answer served from the local cache was never sent to a model at all, so there is nothing to count. Code that reads `usage` should cope with `None`. For this chapter, printing it is enough.

## When the Call Fails

A learning package has one design decision you should know about before it surprises you. `get_response` does not crash your script when something goes wrong. It returns a string that describes the problem, and your `print` shows it like any other answer. That is kind to beginners in a classroom. It also means the variable named `answer` sometimes holds an apology instead of an answer, and any code you build on top of the call has to be able to tell the difference.

You can see the gentlest case without any setup at all.

text
⚠️ Empty prompt.

The empty question never leaves your machine. The package checks for blank text before it builds a request. A harder failure looks like this.

❌ Error: Connection error.

That message means the request was built and sent, twice, and no server answered. The cause is nearly always one of three settings: the server address is wrong or the server is off, the model name does not exist on that server, or a hosted provider rejected the key. Run `handsonai doctor` and read what it resolves your server and model to before you touch your script. The script is five lines long and seldom the problem.

Production code usually signals failure by raising an exception, which stops the program unless the programmer handles it. A teaching package makes a different trade. A string keeps a first lesson moving, and it makes the failure visible in the same place as the success. Later modules in the package keep the same habit. When you graduate to production libraries in , expect exceptions there, and expect to write the handling yourself.

## Where a Demo Can Mislead You

You are now equipped to spot three common exaggerations in AI product demos. Each one dissolves once you ask what was added around the call.

A product claims its assistant "knows your business". Sometimes it does, because someone pasted business documents into the messages list before your question. That is a real technique, and you will build it in . But the knowledge lives in the request, not in the model. Change the documents and the expertise changes with them.

A product claims its assistant "remembers you". It keeps your earlier messages and resends them, so the list carries your name into every call. The effect feels like memory because the transcript is doing the remembering.  builds that transcript by hand and saves it to a file you can open.

A product claims its assistant "checked the latest figures". Its code fetched those figures first and put them in the prompt, or it gave the model tools to fetch with. The bare call you ran in this chapter can do neither. Left alone, the model answers from training, and training ends at a date.  makes that limit visible with a question the model gets confidently wrong.

None of this makes the products dishonest. Knowing the bare call lets you ask which addition a claim rests on, and what happens to the claim when the addition is removed.

# Who the Model Is Being 

> A chatbot with a personality is the call from Chapter 1 plus one string you wrote.

Package companion: the personality bots in `hands_on_ai.chat`. Listings checked against `hands-on-ai` 0.6.0.

Misconception this chapter kills: "The AI has a personality." A system prompt is text in the request, and you can read it, change it, and count what it costs.

The build: one question asked three ways: with no instruction, with your own system prompt, and through a personality bot. Then your own bot, written as a function.

Python you need: passing a named argument, and defining a small function with `def` and `return`. Both are in .

## The Concept First

In  you printed the payload and found a message you had not written. It had the role `system` and the content "You are a helpful assistant." That message goes first in the list, before anything the user says, and the model treats it as standing instructions for the whole exchange.

A system prompt is standing instructions, written by whoever built the product and sent on every call. When a help-desk bot stays polite under provocation, when a study app answers like a tutor and refuses to just hand over the answer, when a novelty app talks like a pirate, the mechanism is the same in each case. Someone wrote a paragraph, put it at the front of the list, and the model's replies bent around it.

Two consequences follow, and this chapter demonstrates both. The personality belongs to the request, so it can be swapped between one call and the next with no change to the model. And the instruction is text like any other text in the payload, so it costs tokens on every call, whether the user sees it or not.

## Understanding Through Real Life

Think of briefing a relief worker who will staff your shop counter for one shift. Before the first customer arrives, you hand them a card. The card says who they are today, how to greet people, what they may promise, and what to do when they do not know something. Every customer conversation then happens inside the frame the card set.

Change the card and the same worker runs a different counter. "You are the returns desk. Be brief. Offer a refund or a replacement, nothing else." produces a different afternoon from "You are our most patient explainer. Walk people through setup one step at a time."

A human reads the card once and remembers it. A model reads the card fresh on every call, because the card is inside every request, and your business pays for the reading each time. A long, careful card can be worth every token. It is still a running cost, and in this chapter you will watch it on the receipt.

## The Build: One Question, Three Answers

Start where Chapter 1 left off. Ask a question with a system prompt of your own.

```python
# Listing 2.1 of 4: your instruction, in the first message (who.py)
from hands_on_ai.chat import get_response

question = "Why is the moon sometimes visible in the daytime?"

print(get_response(question))
print()
print(get_response(
    question,
    system="You are a witty pirate. Talk like a pirate from the 1700s.",
))
Run it. The first answer arrives in the package's default voice, because the default system string from Chapter 1 went along as usual. The second answer explains the same astronomy in nautical slang. The model, server and question string are unchanged; one argument changed.

Read the new argument closely. `system=` is a named argument. It fills the `system` slot of `get_response`, which places your string in the first message of the payload, exactly where the default used to sit. If you want proof rather than my word for it, rebuild the payload printer from Listing 1.2 with your string in the first message and look at the output. The shape is identical and the content is yours.

Try two more while you are here. "Answer in exactly one sentence." tends to hold. "You are a calm and clear teacher. You explain concepts step by step." changes the structure of the answer as well as its flavour. A system prompt can reach tone, length, structure, and what the reply refuses to do. It cannot give the model facts it does not have, and it cannot make the model remember this conversation tomorrow. Facts arrive in Part II. Memory arrives in the next chapter, and it arrives as plumbing, not as instruction.

## The Pirate in a Box

Typing a long instruction at every call gets old fast, so the package wraps common ones in functions with friendly names. These are the personality bots.

```python
# Listing 2.2 of 4: the same pirate, packaged
from hands_on_ai.chat import pirate_bot, teacher_bot

question = "Why is the moon sometimes visible in the daytime?"

print(pirate_bot(question))
print()
print(teacher_bot(question))

There is no new machinery here. Open the source of `pirate_bot` in the package repository and you will find the whole of it, apart from its documentation string, is one line.

```python
# Listing 2.3 of 4: pirate_bot, complete (from the package source)
def pirate_bot(prompt):
    return get_response(prompt, system="You are a witty pirate. Talk like a pirate from the 1700s.", personality="parrot")
Your Listing 2.1 and the package's Listing 2.3 make the same call. The bot just spares you typing the string. The `personality=` argument is a smaller detail with a practical job. It does not go to the model at all. It chooses which set of retry messages the package prints while it reattempts a failed call, so a pirate that hits a network error apologises in character. Two different arguments, two different audiences: `system` instructs the model, `personality` styles the package's own chatter around the call. Keeping straight which text the model sees and which it never sees is a habit that matters more as the wrappers grow.

The package ships thirteen of these bots, from `friendly_bot` and `coder_bot` to `shakespeare_bot` and `caveman_bot`. Every one of them is a function wrapping a call with a system string.

## Write a Bot of Your Own

You have already written everything a bot contains. The last step is wrapping it in a function so you can reuse it by name.

```python
# Listing 2.4 of 4: your own bot (my_bot.py)
from hands_on_ai.chat import get_response

def plain_english_bot(prompt):
    return get_response(
        prompt,
        system=(
            "You explain things in plain English for a reader of about "
            "twelve. Use short sentences. Give one everyday example. "
            "If you must use a technical word, define it in the same sentence."
        ),
    )

print(plain_english_bot("What is compound interest?"))

The `def` line names the function and its one input. The indented lines are its body. `return` hands the result of the inner call back to whoever called your bot, which is why `print` can show it. The system string here is longer than the pirate's because it has a job to do: it sets reading level, sentence length, and a rule for technical words. Instructions that can be checked, like "define it in the same sentence", hold up better than instructions about vibes, like "be clear". You can test that claim yourself in the exercises.

Your bot takes the question as an argument but keeps the instruction fixed. That split is the product pattern from real chatbots: the builder owns the system prompt, the user owns the question, and the user never sees the builder's paragraph. When you use a polished AI product and wonder why it behaves the way it does, a paragraph like this one, written by someone on the product team and sent with every request you make, is usually most of the answer.

## What the Instruction Costs

Chapter 1 ended with a receipt. Use it again, this time on your own bot's inner call. Add `return_usage=True` to the `get_response` call inside a copy of Listing 2.4 and print both values.

Compare two runs of the same question: one with the package default system string, one with your plain-English paragraph. The question did not change. The reply length will wander a little, as replies do. The pattern to look for sits in `prompt_tokens`, which rises by roughly the length of your instruction, because your paragraph rides along in every request.

On a local model this costs you a sliver of time. On a paid provider it is a per-call charge that never switches off, paid by every user on every question, including the ones who ask something trivial. Product teams feel this pressure from both sides. A longer system prompt can buy steadier behaviour, safer refusals, and a voice users recognise. It also taxes every exchange and, in a long conversation, crowds the space available for the conversation itself. The next chapter shows where that space goes. When you write an instruction, ask what it earns per token.

A system prompt that demands one-sentence answers and step-by-step explanations in the same breath forces the model to choose which order to disobey. It will choose quietly, and differently on different runs. When a bot behaves inconsistently, read its card before you blame the model. Contradictions in standing instructions produce wobble that looks exactly like model randomness.

## Where a Demo Can Mislead You

A vendor introduces "our empathetic support agent" or "our strict compliance reviewer" as though a new kind of AI had arrived. You now know to ask a plainer question. What does its system prompt say? Sometimes the honest answer is a well-tested paragraph, refined over months, backed by retrieval and tools from later chapters of this book. # No Memory Between Calls 

> The model forgets you completely between calls. Anything it appears to remember, your code sent again.

Package companion: `Conversation` in `hands_on_ai.chat`. Listings checked against `hands-on-ai` 0.6.0.

Misconception this chapter kills: "It remembers me." Every call is stateless. Memory is a transcript you keep and resend.

The build: a chat that learns your name and uses it. Then its memory, saved to a JSON file you can open, edit, and reload.

Python you need: creating an object from a class, calling its methods with dot notation, and reading a list.  covers the patterns. The word class is explained where it first matters, below.

## The Concept First

At the end of Chapter 2 your bot could not recall your name from one call to the next. That was not a flaw in your bot. It is how the call works. The server receives a payload, produces a reply, and keeps nothing. Your next call is, to the model, the first thing that has ever happened.

Chat products hide this with bookkeeping. The app stores every message, yours and the model's, in order. On each new turn it sends the whole list again: the system instruction from Chapter 2 at the front, then the full conversation so far, then your new question at the end. The model reads the transcript, sees your name in an earlier message, and answers as though it remembered. The memory lives in the app and in the payload, and the model rereads it at full price on every turn.

Three familiar behaviours of chat products follow from this mechanism. Long conversations get slower and dearer, because each turn resends everything before it. Very long conversations start dropping their beginnings, because the payload has a size limit, called the context window. And a fresh chat feels like a stranger, because it is one: a new list with nothing in it but the instruction card.

## Understanding Through Real Life

Return to the well-read stranger who answers your letters, from Chapter 1. Imagine now that the stranger has a strict rule: every letter they receive is shredded the moment the reply is posted. If you want a continuing correspondence, there is exactly one way to have it. Each time you write, you copy the entire exchange so far into your new letter: your first question, their reply, your follow-up, their reply, and finally today's question at the bottom.

Your letters get longer every week. Postage rises with length, so a long correspondence costs more per letter than a short one, even when today's question is a single line. Eventually the envelope reaches the largest size the post office will carry. Past that point something has to give. You can stop writing, start a new correspondence, or quietly leave the earliest pages out of the copy. The stranger will then answer as though those early exchanges never happened, because for them, they never did.

The envelope limit is the context window, measured in tokens. The rising postage is the per-call token cost you met in Chapter 1. The missing early pages are why a long chat can forget the name you gave it an hour ago while remembering what you said a minute ago.

## First, Watch the Forgetting

Prove the statelessness to yourself before building the fix. Two separate calls, using the function you already know.

```python
# Listing 3.1 of 3: two calls, no memory (forgetful.py)
from hands_on_ai.chat import get_response

print(get_response("My name is Sam. Remember it."))
print(get_response("What is my name?"))
The first reply will be warm and reassuring. The second will admit it does not know, or guess, or explain that it has no record of earlier conversations. The model said it would remember because that is a natural thing to say in conversation. The words were produced by the same process that produces everything else it writes. No storage happened behind them. When a person says "I will remember that", a memory forms. When a model says it inside a stateless call, only the sentence exists.

## The Build: a Conversation That Resends

The package does the bookkeeping in a class named `Conversation`. A class is a template for making objects that bundle data with the operations that belong to it. In practical terms for this chapter: you create one conversation object, it holds the message list inside itself, and you talk to it through a method named `ask`.

```python
# Listing 3.2 of 3: the same exchange, with a transcript (remembering.py)
from hands_on_ai.chat import Conversation

chat = Conversation(system="You are a helpful tutor.")

print(chat.ask("My name is Sam."))
print(chat.ask("What is my name?"))
print("Tokens so far:", chat.total_tokens)

Run it, and the second answer gets your name right. Read the listing slowly, and compare it with Listing 3.1. The first line after the import creates the object and hands it the instruction card. That card becomes the first and, for now, only message in its list. The first `ask` appends your message to the list, sends the entire list to the model, receives the reply, and appends the reply to the list as well, under a third role you have not met yet: `assistant`. The second `ask` appends your new question and sends all four messages. The model sees "My name is Sam." in the transcript and answers from it.

The last line prints the running token account. `Conversation` adds up the usage the server reports after each turn and keeps the total where you can read it. Ask a few more questions and print it again. Then do the arithmetic Chapter 1 prepared you for: the tenth turn of a conversation resends the nine before it, so a conversation costs more than the sum of its questions, and the gap widens with every turn. On a local model you pay in waiting time. On a metered provider you pay in money, for rereading.

You have now seen every role a message can carry in this book's early chapters. `system` holds the builder's standing instructions. `user` holds what the person typed. `assistant` holds what the model replied, saved so it can be resent. When you read a saved transcript in the next section, roles are how you tell who said what, and the model relies on the same labels.

## The Memory Is a File

If the memory is a list your code keeps, then it can be written down. `Conversation` will do it for you.

Open `my_chat.json` in any text editor before you run the second half. It is plain JSON, the same format as the payload from Chapter 1, holding five things: the system prompt, the model setting, the personality used for retry messages, the complete `messages` list, and the token total. The object that felt like a mind a moment ago serialises into a page of structured text, and `load` rebuilds the object from that page in a later run, on a later day, on a different machine. The reloaded chat answers with your name because the file carried the transcript across the gap. The model was never consulted about any of it.

First, edit the file by hand. Change "Sam" to "Priya" inside the saved user message, reload, and ask again. The model will call you Priya with complete confidence, because you edited the only record it ever reads. Second, call `later.reset()` and ask once more. `reset` throws the transcript away and keeps only the system prompt, and the name is gone. Products dress these two operations in friendly buttons: edit history, delete conversation. Underneath, someone is keeping, editing, or discarding a list.

The `history()` call in the last line returns the transcript without the system message, which is the view a product would show its user. The instruction card stays in the payload and out of sight, as Chapter 2 described.

## The Window Has Edges

The context window is the largest payload a model will accept, counted in tokens, instruction and transcript and new question together. Windows vary widely by model, from a few thousand tokens to well over a hundred thousand, and the model name in your configuration decides which one you have. Your local model will tell its limit in its documentation, and `handsonai models` can show what your server reports.

`Conversation` in this package resends everything and trims nothing. That honesty is deliberate in a learning tool. It means a very long chat with this class will eventually produce an error from the server, or a reply that behaves as though the beginning never happened, depending on how the server handles an overlong request. Production chat products choose a trimming strategy instead: keep the most recent turns, summarise the older ones into a short paragraph that rides along in place of the originals, or pin a few facts while letting chatter scroll away. Each strategy loses something different, and each is a decision a person made about what the conversation is allowed to forget, and most products never tell their users which decision was taken.

One more edge is already visible in your build. When a call fails, the package returns an error string, as Chapter 1 explained, and `Conversation` appends that string to the transcript as the assistant's turn. A failed exchange becomes part of the record the model rereads on the next turn. In a short lesson that is harmless. In a long session it can confuse matters.

A saved conversation is a complete record of what was said, in a file anyone with the file can read. That makes transcripts wonderful for debugging, teaching, and the audit habits later chapters build. It also means a chat about a medical worry, a legal problem, or a business secret leaves a plain-text copy wherever the app stored it. Before you paste anything sensitive into any AI product, ask where its transcript lives and who can open it. You now know there always is one.

## Where a Demo Can Mislead You

"It remembers everything about you" is a claim about a list. The questions that follow from this chapter are concrete ones. How much of the transcript is resent, and what gets trimmed when the window fills? Where is the transcript stored, for how long, and can you read or delete the actual file rather than trusting a button? When the product says it learned your preferences, did anything change anywhere except the text prepended to your next call? A vendor with good answers built deliberate bookkeeping. A vendor who talks about the model getting to know you is describing that bookkeeping.

# Any Provider Will Do 

> Your scripts name no vendor. Three settings decide whose model answers, and all three live outside your code.

Package companion: configuration and the response cache in `hands-on-ai`. Listings checked against `hands-on-ai` 0.6.0.

Misconception this chapter kills: "I am locked into one vendor." OpenAI-compatible endpoints are a common language, and your code already speaks it.

## The Concept First

Look back at every script you have written so far. None contains a server address, and none names Ollama or any company. The most vendor-specific thing in them is a model name you chose in a payload exercise. And yet the calls worked, because something outside your code supplied the address, the model, and the key. That something is the package configuration, and this chapter opens it.

The configuration can stay outside because one company's API shape became the common dialect. A request is a `POST` to an address ending in `/v1/chat/completions`, carrying the JSON payload from Chapter 1, with the key sent as a standard authorisation header. Dozens of providers now accept that exact shape, whatever their own models are called. Tools that speak the dialect, including this package, can be pointed at any of them by changing an address and a key. The industry calls such services OpenAI-compatible, after the company whose shape won.

Compatibility has limits, and a later section names them. Within those limits, the practical consequence is large: choosing a provider is a settings decision, reversible in a minute, and the code you write against the dialect survives the change.

## Understanding Through Real Life

Think of the SIM card in a phone. The handset holds your apps, your habits, and everything you have built up. The SIM decides whose network carries your calls and whose bill arrives. Swapping networks means swapping a small card and confirming the new signal works. Nobody expects to replace the handset to change carriers, and a phone that demanded it would be returned to the shop.

Your scripts are the handset. The three settings in this chapter are the SIM: the server address, the model name, and the key. A provider who wants you locked in will try to move pieces of value out of your handset and into their network, into features only their dialect extensions can reach. That can be a fair trade when you choose it knowingly. This chapter exists so that you always know which parts of your setup would travel and which would not.

## The Three Settings

The package resolves its configuration in a fixed order, weakest first: built-in defaults, then a config file at `~/.hands-on-ai/config.json`, then environment variables, which win over everything. Chapter 1 ran on the defaults: a local Ollama server at `http://localhost:11434`, the model `llama3`, and no key, because a local server does not check one.

Environment variables are named settings your terminal hands to every program it launches. Three of them steer everything in Part I:

| Variable | Sets | Local default |
|---|---|---|
| `HANDS_ON_AI_SERVER` | The provider's base address | `http://localhost:11434` |
| `HANDS_ON_AI_MODEL` | Which model answers | `llama3` |
| `HANDS_ON_AI_API_KEY` | The key, where one is required | unset |

The address does not need the `/v1` ending; the client adds it when it is missing, so addresses copied from provider documentation work either way. And when no key is set, the client still sends a harmless placeholder, because the underlying library insists on a key-shaped string even though your local server ignores it. You met that placeholder in Listing 1.3.

`handsonai doctor` prints the resolved result of all this: the config file it read, the server and model it will use, and whether a key is configured, shown masked. Whenever you change a setting, run the doctor before you run a script. It reads the same configuration your code will read, in the same order, so an argument with the doctor is an argument you do not have to have with a traceback.

## Local and Hosted: an Honest Comparison

Local Ollama and a hosted provider are both legitimate places to run this book, and they trade differently. A local model is free per call, works offline, and keeps your prompts on your own machine, which matters for the transcript concerns raised in Chapter 3. Its limits are your hardware's limits: smaller models, slower replies, and a smaller context window than the big hosted offerings. A hosted model reverses the trade. It is stronger and faster, it costs money per token, and every prompt travels to someone else's computers under their retention rules.

Neither choice is the permanent one. A classroom can run Monday's lesson locally and Friday's on a hosted model for the harder project. A prototype can start where iteration is free and move when quality demands it. What you should not do is let the choice harden into your code by accident, one vendor-specific feature at a time, until moving would mean starting over.

Compatibility also has edges. The dialect covers the request and reply shape for chat, which is everything Part I has used. It does not standardise every extra a provider offers. Model names differ and must be exact; `handsonai models` lists what your current server reports, which settles most name disputes. Usage reporting varies, so `usage` can be `None` on one provider and complete on another. And two models given identical payloads will still answer differently, in quality, tone, and how literally they follow your system prompt. Portability moves your code without making the models interchangeable, and Part IV's judge exists partly because of that gap.

## The Cache: When Reproducible Beats Fresh

One more setting belongs in this chapter because it changes where answers come from. The package can keep a copy of every reply on disk and serve repeats from the copy instead of calling the model again. It is off until you switch it on:

The first run calls the model and stores the reply in a plain text file inside that directory, named by a hash of the three things that define the call: model, system prompt, and question. The second run finds the file and prints the stored reply without contacting any server. You can prove it to yourself by running the second one with Ollama stopped. It still answers, instantly, in the exact words of the first run.

In a classroom, a teacher can warm the cache once, then thirty students rerun the lesson offline and see identical output, and nobody's exercise breaks because a model felt whimsical that morning. Chapter 11's judge needs stable material to judge, and the cache is how this book gets it. The costs are the mirror image of the benefits. A cached answer never improves when you switch to a better model, because the model is part of the lookup only as a name in the hash, and a stale cache can confuse you into thinking your new settings changed nothing. Cached replies also arrive with `usage` set to `None`, as Chapter 1 warned, because no tokens were spent. And the cache is one more folder of plain-text transcripts on disk, subject to the same care as the saved chats in Chapter 3. Clearing it is deleting the directory.

"Powered by our proprietary AI platform" sometimes means a team built something substantial: retrieval, tools, evaluation, the subjects of Parts II to IV. # What the Model Doesn't Know 

> A model answers from what it learned in training and what you put in the payload. Everything else is improvisation, delivered in the same confident voice.

Package companion: `get_response` from Part I, used twice on the same question. Listings checked against `hands-on-ai` 0.6.0.

Misconception this chapter kills: "It knows everything." Training has a cutoff and a domain, and confidence is a style, not a measurement.

The build: a question your model cannot possibly answer from training, asked bare, then asked again with the answer pasted into the prompt by hand.

Python you need: a multi-line string and an f-string, both in .

## The Concept First

Every answer in Part I came from one of two places. The model was trained, once, on a large collection of text, and that training ended on a particular date with a particular coverage. Call that everything the model learned at school. The second source is your payload: the system instruction, the transcript, and your question. There is no third source. The bare call you have been making cannot look anything up, cannot check today's news, and cannot read your documents unless you put them in the request.

Trouble starts because the model does not experience the boundary between those sources as a wall. Its job is to produce a plausible continuation of the conversation, and it does that job with the same fluency whether the material under it is solid training knowledge, your supplied text, or nothing at all. Given a question it cannot answer from either source, it will often still answer, composing something that sounds like the kind of reply such a question usually gets. The industry calls an invented answer of that kind a hallucination. The word suggests a malfunction, and that suggestion misleads: the machinery did what it always does, in a place where it had nothing true to work with. Hallucination is a property of the setup, best managed by changing the setup.

If invented answers are what a model produces when the payload lacks the facts, then the fix is to put the facts in the payload and instruct the model to stay inside them. This chapter does that by hand, with copy and paste. The next chapter automates it.

## Understanding Through Real Life

Think of a brilliant, well-read colleague who joined your organisation this morning. Ask her how double-entry bookkeeping works and you will get a superb answer: she learned it long before she met you. Ask her what your team's refund limit is, and a careful person says she does not know yet and asks where the policy lives. A model, asked the same question in the same bare way, frequently produces a number. The number will be formatted like a policy. It may even be a sensible number. It will not be your limit, because your limit is written in a document she has never seen, and no amount of general brilliance substitutes for reading it.

The failure sits with the request: somebody asked for an internal fact without handing over the internal document, and accepted fluency as a substitute for the hand-over. Organisations run on facts of the kind no training set contains: this term's timetable, your pricing, your house rules, what was decided in Tuesday's meeting. Every one of those questions needs the document in the room.

## The Build: Ask for What It Cannot Have

You need a fact the model cannot have from training. The surest supply is a small organisation of your own invention. This listing asks about one.

python

## What Asking Bare Questions Costs

A bare question about general knowledge is cheap and often fine. A bare question about your documents, your customers, or last week costs you a check you probably will not do, because the answer arrives formatted as though the check already happened. The expensive moment is the decision made from a fluent invention by someone who had no reason to suspect it.

Three questions sort most requests before you send them. Could the model have learned this in training, from public text written before its cutoff? Is the fact stable, or could it have changed since? And if the answer were invented, who would find out, and when? A question that fails the first two tests and embarrasses you on the third does not need a better model. It needs its evidence in the payload, which from the next chapter onward your code will supply.

People sometimes ask a model how confident it is, hoping the number separates knowledge from invention. Treat the reply as more generated text. A model can produce "I am 95% certain" for the same reason it produces any fluent sentence: such sentences appear in its training, attached to right and wrong answers alike. The checks that actually separate the two are external: evidence in the prompt, a source you can open, a second method, a judge measured against examples. This book builds those, in that order.

## Where a Demo Can Mislead You

A demo question is chosen by the demonstrator, and demonstrators instinctively choose questions training covers well. The model shines, and the audience generalises the shine to their own questions, which live in documents training has never seen. When you watch any AI demo from here on, keep one question of your own ready: a fact from your world, recent or internal, that you can verify on the spot. Watch what the system does with that question, and whether it can show you its source.

# Chunk, Fetch, Answer 

> Retrieval-augmented generation is the paste you did by hand in Chapter 5, with code doing the searching and the pasting.

Package companion: `hands_on_ai.rag`, plus the `rag` command-line tool. Listings checked against `hands-on-ai` 0.6.0.

Misconception this chapter kills: "RAG is a framework." It is search, then a prompt with the search results in it.

The build: `first-rag-bot`, the package's first RAG project. Index a small folder of documents, then ask questions and get answers that name their sources.

Python you need: loops, lists, dictionaries, and f-strings building a long string. All are in .

## The Concept First

Chapter 5 ended with a shape: select relevant text, paste it into the prompt ahead of the question, instruct the model to answer from the text. The technique has a name in the research literature, retrieval-augmented generation, from the paper that popularised it [@lewis2020rag], and the industry shortens it to RAG. The name sounds like a product category, but nothing has changed about the call. The model still receives one payload and returns text. What changed is who does the selecting and the pasting: code, in the seconds before the call.

The work splits into two phases that happen at different times. Indexing happens once, before any question is asked: load the documents, cut them into chunks, turn each chunk into numbers a search can compare, and save the lot to a file. Answering happens per question: turn the question into numbers the same way, fetch the chunks whose numbers sit closest, assemble them into a prompt of exactly the shape you built by hand, and make the familiar call. Every concept in this chapter lives in one of those two phases, and keeping them apart in your head prevents most confusion about RAG systems, including expensive commercial ones.

## Understanding Through Real Life

Picture a reference librarian working from index cards. Long before you arrive, someone read every book in the collection and wrote a card per passage: a short excerpt, the book it came from, and a code describing what the passage is about. That is indexing, done once, at leisure. When you arrive with a question, the librarian does not reread the library. She works out which code your question carries, pulls the handful of cards whose codes sit closest, and hands you those passages with their book titles attached. You read five passages instead of five shelves, and you can check each claim against the book named on its card.

Two details of the card system carry over. The codes were designed so that passages about similar things get similar codes, even when they share no wording: a passage about returning library books late and your question about overdue fines should land near each other. And the system can only ever hand you cards that exist. A book nobody indexed is invisible, however relevant, and a card written from last year's edition keeps describing last year's rules until somebody redoes the indexing.

## Connect a Second Model Before You Build

The codes on the cards are produced by an embedding model. An embedding model is a relative of the chat models you have used so far, with a narrower job: it reads a piece of text and returns a long list of numbers, called an embedding or a vector, that captures what the text is about. Texts about similar things produce lists that point in similar directions, and comparing directions is arithmetic your code can do quickly. The package configuration names an embedding model separately from the chat model, defaulting to `nomic-embed-text`. Pull it the same way you pulled your chat model:

python
# Listing 6.1 of 4: get the sample documents (get_docs.py)
from hands_on_ai.rag import copy_sample_docs, list_sample_docs

print(list_sample_docs())
print(copy_sample_docs("sample_docs"))

The folder contains a handful of files in the formats the package can load: `.txt`, `.md`, `.docx`, and `.pdf`. Reading them needs no model at all. Text and markdown files are read as they are, Word documents surrender their paragraphs, and PDFs surrender the text of each page. Your own documents can join the folder at any time, as long as they wear one of those four endings.

## Chunk: Cut the Documents Into Cards

Indexing begins with cutting. `load_text_file` reads a file into one long string, and `chunk_text` splits the string into chunks of a set number of words. The configured default is 500 words per chunk. That number is far too large to see anything at a glance, so this listing uses five:

text
'A member may borrow up'
'to four books at once.'
'The loan period is three'
'weeks.'

Read that output closely. The cutting is purely mechanical: count words, slice, repeat. It knows nothing about sentences, so a rule can be severed from its number, as "four" nearly was here. Real chunk sizes soften this. At 500 words, most facts survive inside one chunk, and a question usually needs only one or two chunks to answer. The tension remains: small chunks make search precise and risk amputating the answer. Large chunks keep context intact and spend your token budget on text the question never needed, three chunks at 500 words being a fair slice of a modest context window before the conversation even starts.

`chunk_text` also does not overlap chunks. Production systems often let neighbouring chunks share a margin of text so a severed sentence appears whole in at least one card. This package keeps the simpler cut, and the simplicity is instructive. When your bot later misses an answer that straddles a boundary, you will know a named cause to investigate first.

## Fetch: Numbers That Find Their Neighbours

With chunks cut, indexing finishes the cards. `get_embeddings` sends each chunk to the embedding model, through the same server and the same kind of client as Chapter 1's call, at the related address `/v1/embeddings`. Back comes one list of numbers per chunk. `save_index_with_sources` then writes a single file, conventionally `index.npz`, holding three parallel lists: the vectors, the chunk texts, and for each chunk the path of the file it came from. That third list is the book title on the librarian's card, and it is what later lets an answer name its sources.

Fetching at question time mirrors the process. The question goes to the embedding model and comes back as one more list of numbers. Then a similarity score, cosine similarity, compares the question's direction with every chunk's direction and produces a number per chunk: near 1 for chunks about much the same thing, lower as topics drift apart. `get_top_k` sorts those scores, takes the best `k` of them (three unless you say otherwise), and returns the winning chunks paired with their sources. Stripped to its skeleton, the whole retrieval is four moves: load the index file, embed the query, score every vector against it, keep the top few. A vector database, when a vendor mentions one, is a faster and larger home for those same four moves.

Similarity search has two limits. Closeness is about topic, not about truth or importance, so a chunk can score well by discussing your subject without containing your answer. And the question's wording steers the fetch: asking with the documents' vocabulary retrieves better than asking around the subject, which is why rephrasing a failed question is a real debugging step and not superstition.

## Answer: Assemble the Prompt You Already Know

The package's own `rag ask` command builds the prompt by listing the fetched chunks under a "Context:" heading, appends an instruction to answer from the context and to say so when the context lacks the answer, sets a system prompt demanding answers based only on the provided context, and calls `get_response`. It is Listing 5.2 with the paste automated. This listing does the same job in your own code, printing the sources so you can check them:

```python
# Listing 6.3 of 4: fetch, assemble, answer (ask_docs.py)
from hands_on_ai.chat import get_response
from hands_on_ai.rag import get_top_k

question = "What does TCP do?"

results = get_top_k(question, "index.npz", k=3)

prompt = f"Question: {question}\n\nContext:\n"
for chunk, source in results:
    prompt += f"- {chunk}\n"
prompt += (
    "\nAnswer the question based on the provided context. "
    "If the context doesn't contain the answer, say so."
)

answer = get_response(
    prompt,
    system="You are a helpful assistant that answers questions "
           "based only on the provided context.",
)

print(answer)
print("\nSources:")
for chunk, source in results:
    print("-", source)
Before this can run, an index must exist. The command-line tool builds one from a folder in a single step, which is how the package's `first-rag-bot` project starts:

```bash

By default the index lands at `~/.hands-on-ai/index.npz`, where `rag ask` looks for it, and `--force` permits rebuilding over an older index. The two flags on the question are the chapter's debugging instruments. `--context` shows the chunks the fetch chose, and `--scores` shows how close each one scored. When an answer disappoints, look there before you touch the prompt. Most bad RAG answers are faithful summaries of the wrong chunks, and no instruction to the model can repair evidence that was never fetched.

Run both routes on the networking samples. Ask what TCP does, how HTTP works, and what distinguishes TCP from UDP, the starter questions from the project guide. Indexing reads the documents as they were at indexing time. Edit a document afterwards and the bot keeps answering from the old text, confidently and with citations, until somebody rebuilds the index. Stale indexes are the quietest failure in RAG systems because nothing errors: the fetch works, the answer is fluent, the source file exists. Only the content moved. Any team running RAG in earnest needs a rebuild habit tied to how its documents change, and now you know why that sentence belongs in their design rather than their apologies.

# Giving the Model Hands 

> A tool is an ordinary Python function. The model's new power is being allowed to ask for it by name.

Package companion: `hands_on_ai.agent`, its tool registry, and the built-in calculator. Listings checked against `hands-on-ai` 0.6.0.

Misconception this chapter kills: "Agents are products you buy." An agent begins the moment a model may request a function and your code decides whether to run it.

The build: one registered calculator the model can ask for, called directly so you can watch it work without the model, then a tool of your own.

Python you need: functions and function arguments from . One system in this chapter passes a function itself as an argument, and that move is explained where it happens.

## The Concept First

Everything your model has done so far ends in text: it answers, adopts a voice, rereads a transcript, and summarises fetched chunks. It cannot add two numbers reliably, read today's date, look inside a file, or check anything outside the payload. Tool use changes the shape of the exchange. Alongside your question, the payload now carries descriptions of functions your code is willing to run. The model may reply with a request to run a named function with a given input. Your code runs it, or refuses to, and sends the result back as another message. The model then answers with the result in hand.

The model never executes anything; it cannot. It produces text, and one shape of that text is a request for a named function. Your program parses the request, checks the name against a registry you control, calls the function with the requested input, and returns the output as text. Every security question in this chapter, and most of Part IV, grows from that division of labour: the model proposes, your code disposes.

Three pieces make the arrangement work. The registry is a table of allowed functions, each with a name and a description. The description is what the model reads, so the description is the interface: a tool whose description is vague or wrong will be called wrongly, however good the function is. And the result comes back as a message in the transcript, an observation, where the model can read it on the next turn: another job for Chapter 3's list.

## Understanding Through Real Life

Think of advising a colleague by phone while they stand in a workshop you cannot enter. You cannot touch anything. What you can do is say: use the torque wrench on the second bolt, and tell me what the gauge reads. Your colleague, who has the hands, decides whether that instruction makes sense, carries it out, and reports the reading. You reason again from the report.

The voice on the phone can be brilliant and can also ask for the wrong tool, the right tool with a nonsense setting, or a tool that does not exist on the bench. The person holding the tools stays responsible for what gets picked up. When a product advertises an agent that "takes action", translate it into this scene and ask who built the bench, who stocked it, and what the hands refuse to do.

## The Build: One Tool the Model Can Request

The package ships a calculator tool, and registering it takes one call. Registration adds an entry to the registry table: a name, a description for the model to read, and the function itself.

```python
# Listing 7.1 of 3: a model that may ask for a calculator (first_tool.py)
from hands_on_ai.agent import list_tools, register_calculator_tool, run_agent

register_calculator_tool()
print(list_tools())

answer = run_agent("What is 25 * 3?")
print(answer)
The `list_tools()` line prints the registry as the model will effectively meet it: a list of names with descriptions. Run the script and read that output before the answer arrives. Then watch what the run returns. Somewhere between your question and the printed answer, the model asked for the calculator with the input `25 * 3`, your side of the program evaluated it, and the result rode back into the conversation. Chapter 8 slows that exchange down until every hop is visible.

You will not see the request itself in this run. By default, `run_agent` chooses how the model should phrase its requests based on the model you configured. Capable models get a readable text format, the subject of Chapter 8. Small local models, including the default from Part I, get routed to a stricter JSON format, where the request arrives as structured data naming a thought, a tool, and an input, validated before anything runs. Either way, what reaches your registry is a name and a string.

## Call the Tool Yourself First

Take the model out of the loop entirely to understand a tool. The calculator is a Python function, and you can call it the way you called every function in Appendix A:

```python
# Listing 7.2 of 3: the tool, no model involved (tool_directly.py)
from hands_on_ai.agent.tools.calculator import calculator

print(calculator("2 + 2 * 10"))
print(calculator("{'expression': '2 + 2 * 10'}"))

Result: 22
Error: Could not evaluate expression. Dict is not allowed

The first line is the tool working as intended. The second line fails. Look back at the description `list_tools()` printed in Listing 7.1: its example input is written as `{'expression': '2 + 2 * 10'}`, dictionary-style. The function, however, receives one string and evaluates the expression inside it, so a model that follows the description's example literally will send the dictionary text and get an error in return. The failure sits in the interface between them: one sentence of description.

When a tool fails inside an agent run, the failure does not stop the program. The error text becomes the observation sent back to the model, which gets a chance to read it and try again with a corrected input. The same happens when the model invents a tool name: the reply from your side reads `Error: Tool 'nonexistent' not found.` It is a forgiving design for learning, and a design whose risks the safety section below takes seriously, because a model that can retry can also be steered by whatever text a tool returns.

While you have the tool open in front of you, look at how it evaluates. Your first instinct for a calculator might be Python's built-in `eval`, which runs a string as code. The package refuses that route on purpose. Its calculator parses the expression into a tree and walks only the arithmetic nodes it allows: numbers, the basic operators, a short list of named functions. A request to open a file or reach the operating system finds no path in. That is why the dictionary input failed with "Dict is not allowed" instead of being politely evaluated. The allowlist rejected a whole category of input without caring whether this particular instance was harmless.

## Register a Tool of Your Own

A tool of yours needs three things the calculator already showed you: a function that takes one string and returns text, a name, and a description written for its reader, who is a model deciding from that sentence alone whether and how to call it.

One line in that listing does something new. The third argument to `register_tool` is `count_words` with no parentheses after it. That hands the function itself to the registry without calling it, so the registry can call it later when a request arrives. Parentheses would run it immediately, with no input, and register the resulting text instead, which fails in ways worth seeing once in the exercises.

The description earns its keep by preventing the failure you just studied. It names the input's exact shape, including what not to add around it. When you write descriptions of your own, write the example input as the literal string the function should receive, then test the description the way Listing 7.2 tested the calculator's: feed the tool exactly what its description tells the model to send. If that string errors, the description is wrong, whatever the function does with well-formed input.

## The Bench Rules: Safety Lives on Your Side

Everything in this section follows from one fact: text produced by a model, influenced by whoever wrote the prompt and whatever the retrieved documents say, is about to select functions in your process. Treat tool design as designing what that text can reach.

Stock the bench narrowly. A calculator that accepts arithmetic only, a word counter, a lookup that reads one file: each tool should do one small thing, take one plainly shaped input, and have no side effects you would mind explaining. The dangerous tool is the general one, a `run_command` or `evaluate_code` that turns model text into machine instructions. The package's own calculator shows the alternative pattern: parse the input, walk an allowlist, reject everything else wholesale.

Check what each tool actually returns before you trust it in a chain. The package is honest about its teaching tools, and reading two of them is a useful exercise in professional suspicion. Its weather tool is labelled simulated and returns random conditions. Its search tool is also simulated, answering from a small set of canned passages. An agent using them will produce fluent answers grounded in theatre, and nothing in the final answer warns the reader. Tools are evidence sources like the chunks in Chapter 6, and they deserve the same question: where does this text actually come from?

The model can ask, repeatedly and creatively, and the error-as-observation design means it gets feedback and retries. Your registry is the complete list of what asking can achieve. A function that is not registered cannot be called, whatever the prompt says, and a registered function should be safe when called with the worst string a model can produce, as well as the strings you imagined. Chapter 10 adds stopping rules and budgets around the asking.

The tool descriptions ride inside the system prompt the agent sends on every call, so they cost prompt tokens on every iteration, exactly as Chapter 2's standing instructions do. They also compete with each other: two tools with overlapping descriptions will be confused with each other, and the fix is usually in the wording, not the model. When an agent picks the wrong tool, read the bench card before blaming the voice on the phone.

## Where a Demo Can Mislead You

Agent demos love the moment the system "does something" in the real world: sends the email, updates the record, books the thing. The model requested an action in text, and somebody's code decided the request was acceptable and carried it out. What is the full registry this product exposes, and which entries change the world rather than read it? What inputs are validated against an allowlist, and what happens on the worst string, not the demo string? Which tools are real integrations and which are simulations wearing the same costume? And when a tool errors or returns hostile text, does the loop retry blindly, because a system that treats tool output as trusted instruction has handed the phone to whoever wrote the tool's data.

# The ReAct Loop 

> Thought, action, observation, repeat. The thinking is text you can read, and the loop is code you already know how to read.

Package companion: `run_agent` in `hands_on_ai.agent`, forced to its readable text format. Listings checked against `hands-on-ai` 0.6.0.

Misconception this chapter kills: "The agent thinks." It reasons in text, acts through your functions, observes the results, and repeats, inside a loop with stated stopping conditions.

The build: a two-tool agent answering a question neither tool can settle alone, run in the format where every step is legible.

Python you need: the loop idea from  at reading level. The one new pattern, reasoning written out as labelled text, is the chapter itself.

## The Concept First

Chapter 7 gave the model one move: request a function, receive the result. Most interesting tasks need the move repeated with judgement about what to do next. ReAct, short for reason and act, is the pattern that organises the repetition [@yao2023react]. The model writes its reasoning as text labelled `Thought:`, follows it with a requested `Action:` and `Action Input:`, your code appends the result as an `Observation:`, and the model reads the growing transcript and writes the next thought. When it judges the question answered, it writes `Final Answer:` instead. The transcript of an agent run is Chapter 3's message list wearing name tags.

The reasoning is ordinary model output, produced the same way as any paragraph in this book, which means you can read it, save it, argue with it, and catch it in an error before the error becomes an action. The loop that drives it is a short Python `for` loop in the package: call the model, scan the reply for an action or a final answer, run any requested tool, append the observation, go around again. An agent, at this size, is a loop and a labelling convention around the call from Chapter 1.

## Understanding Through Real Life

Think of working a problem aloud with a notebook while a colleague fetches things. You say what you are trying to establish. You ask for one specific thing: the manual, a measurement, a date from the file. Your colleague brings it, you write down what it shows, and the written record changes what you ask for next. At some point the notebook contains enough, and you say the answer out loud.

The notebook is doing quiet work in that scene. Because each step was written, your colleague can spot that you asked for the wrong manual before the wrong part gets ordered. You can backtrack to where a wrong reading entered. And anyone later can replay how the answer was reached, step by step, instead of trusting that it was. An agent trace is that notebook. Treat products that hide the trace the way you would treat a colleague who will not show their workings.

## The Build: Two Tools, One Question Each Cannot Finish

Register the calculator beside your word counter from Chapter 7, then ask a question that needs both, in sequence. To watch the steps in their readable form, this listing asks for the ReAct text format explicitly:

text
Question: How many words are in the sentence 'the model proposes and
the code disposes', and what is that number squared?
Thought: I need a word count first, then a square. The count_words
tool takes the text itself.
Action: count_words
Action Input: the model proposes and the code disposes
Observation: The text has 7 words.
Thought: Now I need 7 squared, which is a job for the calculator.
Action: calculator
Action Input: 7  2
Observation: Result: 49
Thought: I have both numbers.
Final Answer: The sentence has 7 words, and 7 squared is 49.

Read the transcript as a work record. The first thought decomposes the question into an order of operations. The first action's input respects the description you wrote in Chapter 7: the text itself, no labels. The observation is your function's return value, word for word, entering the transcript where the model can use it. The second thought plans from a fact it did not have one turn earlier, supplied by your code rather than its training and carried by Chapter 3's resent list. Both numbers in the final answer came from tools whose work you can inspect.

The readable format is the demanding one. The model must keep the labels exact while reasoning, and small local models often drop a colon, rename a label, or answer inside a thought. That is why `run_agent` defaults to choosing the format for you, routing smaller models to the JSON format from Chapter 7 where a schema validates each reply before anything runs. Forcing `format="react"` on a small model is a fine experiment and a common first failure. Second, `verbose=True` routes the steps through the package's logging, which stays quiet at its default level. To see the steps live, run with the environment variable `HANDS_ON_AI_LOG=debug` set, the same debugging switch the configuration chapter prepared you for.

## Read the Loop

The package's ReAct loop fits on a screen, and reading it in `agent/core.py` is this chapter's version of Chapter 1's payload print. In spirit, stripped of its logging and fallback handling, it does this:

# Listing 8.2 of 2: the loop's skeleton, simplified from agent/core.py
messages = [system_message_with_tools, your_question]

for i in range(max_iterations):
    response = get_response(prompt=transcript_so_far, system=system_message)

    if "Final Answer:" in response:
        return the_final_answer

    tool_calls = parse_action_lines(response)
    if not tool_calls:
        return response

    for tool_name, tool_input in tool_calls:
        result = execute_if_registered(tool_name, tool_input)
        append response, then f"Observation: {result}", to messages

return a_partial_answer_or_an_admission

The system message is Chapter 2's instruction card, here carrying the format rules and the tool descriptions from Chapter 7. The transcript resent on every iteration is Chapter 3's list, which means each turn of the loop is a full model call at full token cost, a fact Part IV's budgets take seriously. The parser is unglamorous text matching: lines beginning `Action:` and `Action Input:` are paired up in order, which is as fragile as it sounds and explains the JSON alternative. Execution is Chapter 7's registry check, including the error-string behaviour for unknown names and failed tools, fed back as the next observation. If someone describes an agent framework to you in terms that cannot be mapped onto this skeleton plus better furniture, ask which line of the skeleton their feature replaces.

## What Makes It Stop

A loop that can always take one more step will, on some question, take all of them. This one has three exits.

The intended exit is the model's own verdict: a `Final Answer:` line, whose text `run_agent` extracts and returns. The second exit is quieter. If a reply contains no tool request and no final answer, the loop treats the reply itself as a direct answer and returns it. That covers questions needing no tools, and also covers a model that lost the format mid-run, which matters when you debug: a plausible-looking reply may be a formatting failure wearing an answer's clothes. The third exit is the budget: `max_iterations`, five by default. When the loop exhausts it, the package tries to salvage the last thought into a partial report, beginning along the lines of "I've been working on this but haven't reached a final answer", and otherwise admits it reached the maximum number of tool calls.

Each exit has a misuse to watch. A model can declare a final answer early, from training, without calling the tools you stocked for exactly that question; the trace exposes it, which is one more reason to keep traces. A model can also circle: request the same tool with the same input, receive the same observation, and think the same thought again until the budget ends. And because every iteration resends the transcript, a looping agent's turns get dearer as they get less useful. Chapter 10 puts goals and ratchets around repetition. Before running any agent, including one in a product, ask what its three exits are and which one fired.

Take a run that produced a correct final answer and reread its thoughts critically. A right answer can travel through a wrong reason ("squaring counts the words twice") rescued by a tool computing correctly anyway. The answer grades well and the reasoning would fail the next question. Traces let you mark the reasoning, which is the part that generalises, and Chapter 11's judge automates a version of exactly that marking.

## Where a Demo Can Mislead You

Agent demos are edited like cooking shows: a question goes in, a flurry of impressive steps crosses the screen, a polished result comes out. Can I read the full trace of that run, including the tool inputs and the raw observations? How many model calls did it make, and what would they cost at my volume? Which exit ended the run, and what does the trace look like on the runs that hit the iteration budget? Where the vendor says the agent "reasoned", can they show you the sentences, and do the sentences actually support the answer? A demo that cannot show a trace asks you to trust the model's own account of its work.

# Workflows as Folders 

> A workflow can be a folder of numbered stages, each one a readable file, with a person reviewing the output before the next stage runs.

Package companion: `hands_on_ai.workflow`, the `Pipeline` class and `init_workspace`. Listings checked against `hands-on-ai` 0.6.0.

Misconception this chapter kills: "Orchestration needs a framework." Numbered folders of reviewable stages are enough to see, steer, and restart a multi-step job.

The build: a three-stage pipeline, research then outline then draft, run one stage at a time with your review in between.

Python you need: objects and methods from , at the level Chapter 3 used them.

## The Concept First

Part III chained steps inside one run, at machine speed, in a transcript you had to go looking for. That suits a two-step calculation. It suits a report, a lesson plan, or a grant draft much worse, because the moment you most want is the pause between steps: read what the research stage gathered before the drafting stage builds on it, fix the outline before prose hardens around it, stop the line cheaply. A workflow makes that pause part of the structure.

The package implements workflows as folders. A workspace holds numbered stage folders. Each stage folder holds a `CONTEXT.md`, plain-language instructions for that stage, and an `output` folder. Running a stage means assembling one familiar call: a shared system instruction, the stage's contract, any reference rules, and the previous stage's output file as input. The reply is written to `output/output.md`, and then everything stops until a person has read that file and asked for the next stage. The package calls the method ICM, for Interpretable Context Methodology: the context at every step is a file a person can open, rather than state inside a framework you must take on faith.

There is no scheduler, message queue, graph language, or agent hierarchy. The number in the folder name gives the order, the file system gives the memory (Chapter 3's saved-transcript trick at a larger grain), and you, with a text editor, do the review. Because the input to each stage is literally the previous output file, your edits become that input word for word.

## Understanding Through Real Life

Think of a production line with inspection benches between stations. Work arrives at a station with its job card, gets transformed, and sits in the out-tray until an inspector passes it to the next station. The inspector can send a piece back, correct a small flaw by hand and pass it on, or stop the whole line when a station's job card turns out to be wrong. Nobody confuses the line with magic because you can walk it, bench by bench, and see the state of every piece at a glance.

The folder workspace is that line. Stage folders are stations, `CONTEXT.md` files are job cards, `output.md` in the out-tray is the work so far, and `status()` is the glance down the line. The contrast with Chapter 8's loop is deliberate: the ReAct loop optimises for a machine deciding its own next step quickly; the pipeline optimises for a person deciding whether the last step deserves a next one. Most work worth doing with AI has a cheapest point of intervention, and it is usually between stages, before an error gets three stages of polish applied to it.

## The Build: Three Stages, Two Pauses

One function lays out the line:

text
  [ ] 01_research
  [ ] 02_outline
  [ ] 03_draft
[('01_research', False), ('02_outline', False), ('03_draft', False)]

Open the workspace in your file browser and look at what was made. A top-level `CONTEXT.md` holds the shared instruction, which becomes the system prompt for every stage, as Chapter 2's card did for one call. Under `stages/`, each numbered folder holds its own `CONTEXT.md`, created as a stub asking you to describe the stage's job, and an empty `output` folder. A `references/` folder waits at the top level for stable rules, house style, a marking rubric, anything every stage should obey; the runner folds every markdown file in it into each stage's prompt under a references heading. The package calls that folder the factory, by which it means the part of the setup you tune once while the workpieces flow through.

Your job before any model runs is to write the three job cards. In `01_research/CONTEXT.md`, describe the gathering job: the topic, what counts as a useful finding, and the shape to return, perhaps five findings each with a one-line implication. In `02_outline`, ask for an outline built only from the research output, with a named section per decision the board must make. In `03_draft`, ask for prose following the outline, at a stated length, introducing no fact the research stage did not supply. Writing those cards is Chapter 2's instruction craft and Chapter 5's grounding discipline, applied per stage. Vague cards produce vague stations, and no pipeline design rescues them. A `CONTEXT.md` job card is a skill in embryo: a reusable instruction file an agent loads when a task matches. When the same card survives a second run, it can become a reusable skill file. Build Web, Guide AI, "The Agent-Ready Repo and Handover", shows that progression.

Then run the line, one station at a time:

Each `run_next` call finds the first stage whose output file is missing or empty, assembles its call, writes the reply, and returns a small dictionary naming the stage, the output path, and the text. When every stage has a non-empty output, it returns `None` and does nothing. That definition of done, a non-empty `output.md`, is simple enough to reason about at the bench. Edit an output and you have edited the next stage's input. Delete an output and that stage becomes the next one to run again. Clear every output, which the `reset()` method does in one call, and the line restarts from the first station with the same job cards.

## Read the Assembly

One stage's call uses only Part I parts. The system prompt is the workspace `CONTEXT.md` if you wrote one, or a careful default about executing one stage exactly. The prompt is the stage contract first, then the reference rules under their heading if any exist, then the previous stage's output under an input heading, joined into one string. That string goes to `get_response`, and the reply is written to disk verbatim.

Two consequences follow. Stage boundaries are context boundaries: the drafting stage sees the outline file and its own card, not the research transcript, not the road not taken, not your reasoning at the review bench unless you wrote it into the file. Whatever must survive a boundary must be written in the workpiece, which is why good stage contracts ask outputs to carry their evidence with them. And a failed stage leaves its failure in the out-tray, literally: as Chapter 1 established, a connection error comes back as a string, so `output.md` can contain an error message, non-empty and therefore "done" by the runner's rule, quietly feeding the next stage. On this design, the review pause is the error handling.

The runner also offers `run_all`, which fires the remaining stages in sequence with no pause, bounded by a generous step limit. The package documentation is blunt that it is for pipelines you already trust. Treat your first run of any new line as untrusted by definition. Use `run_all` only after the cards have survived a few inspected runs. Even then, the saved files mean a bad run can be rewound stage by stage rather than rerun from a blank prompt.

When a pipeline disappoints, the fix almost never lives in the runner, which only assembles and files. It lives in a job card: the research card did not say what a finding looks like, the outline card did not forbid new facts, the draft card never named its reader. Iterate on `CONTEXT.md` files the way Chapter 7 taught you to iterate on tool descriptions, by feeding the stage exactly what its card requests and reading what the card, as written, actually asked for.

## Where a Demo Can Mislead You

"Fully autonomous multi-agent workflow" demos run the whole line at speed and show the finished piece. Can I see the workpiece between stages, as a file or its equivalent, and edit it before the next stage consumes it? If stage two of five goes wrong, do we rerun one stage or the universe? Where do the standing rules live, and can a person change them without a deployment? When a stage fails, does the failure stop the line in a visible tray, or flow downstream dressed as content? A framework that answers those well has earned its complexity over numbered folders. One that cannot show you the stages gives you nothing to inspect.

## Chapter Summary

- Running a stage assembles one ordinary call: workspace instruction as system prompt, then contract, reference rules, and the previous stage's output as the prompt.

- An error string from a failed call is non-empty, so it counts as done. The review pause is the error handling.

# Loops with a Goal 

> Do, check, repeat is a fine engine and a terrible plan, until the check is a goal you can state and the repetitions have a budget.

Package companion: `hands_on_ai.loop`, with `run_loop`, `run_ratchet`, and `judged`. Listings checked against `hands-on-ai` 0.6.0.

Misconception this chapter kills: "More steps means better." Repetition needs a stopping condition, and progress needs a memory of the best so far.

The build: a rough paragraph improved by a loop until a stated standard is met, twice: once keeping whatever the last step produced, once keeping only improvements.

Python you need: passing a function as an argument, first met in , and the one-line functions written with `lambda`, explained below. The rest is .

## The Concept First

Chapter 8's agent loop repeated until the model declared an answer. This chapter's loop is the same shape with the roles clarified and handed to you. A `step` function does one piece of work to the current state. A `goal` function inspects the new state and returns `True` when it is good enough. The runner alternates them, keeping a history, until the goal fires or a budget of iterations runs out. Do, check, repeat, with the check written down before the doing starts.

Without a stated goal, a loop around a model will happily polish for as many iterations as you fund, including the iterations where the text gets longer, greasier, and worse, because nothing in "improve this" contains a stopping point or a direction of improvement that two readers would agree on. With a goal, two honest outcomes become possible: the loop can report that it met the standard in this many iterations, or that it spent its budget without meeting it. A loop that always returns its last attempt gives you neither report.

The package names the two parts for you. The trigger is the starting state plus the step that fires every turn. The goal is the stopping check, and it can be anything callable that answers yes or no about a state: a word count under a limit, a required phrase present, a test suite passing in your own code, or, from the next chapter's machinery, a model judging the output against criteria and scoring it high enough.

## Understanding Through Real Life

Think of kneading dough to the windowpane test. The step is kneading for a minute. The goal is not "knead until it seems right". It is a stated check: stretch a small piece until light passes through it without tearing. A baker checks after each round, stops the moment the test passes, and knows that kneading past the test does damage rather than adding quality. There is also a budget in practice: if the test has not passed after a reasonable effort, something upstream is wrong with the flour or the water, and more kneading will not rescue it. The honest report is "test not passed in the time", followed by a different decision.

A goal-checked loop is that bakery discipline for text. The windowpane test must exist before the kneading starts, must be cheap enough to run every round, and must be capable of failing.

## The Build, First Without a Model

The runner does not care whether a step calls a model, which makes it possible to learn the shape with plain Python and exact output. This loop builds a sentence one word at a time until it is long enough:

text
start word word word
3 True
['start word', 'start word word', 'start word word word']

Read the return value as a small report, because it is the same report your model versions will give you. `result` is the final state. `iterations` counts the steps that actually ran. `met_goal` tells you which exit fired: the goal's `True`, or the budget running out first. `history` holds every intermediate state in order, the loop's equivalent of Chapter 8's trace, and it is where you will later watch quality rise, stall, or decay. The `lambda` in the listing is Python's way of writing a tiny unnamed function in one line: `lambda text: ...` defines a function taking `text` and returning the value after the colon. Chapter 7 handed named functions to a registry; loops take one-line functions so often that the shorthand earns its place here.

Set `max_iters=2` and run it again in your head: the same step, the same goal, and the report changes to three words, two iterations, `met_goal` false. Nothing failed; the loop tells the truth about a budget too small for its goal, and hands the decision back to you.

## The Build, With a Model and a Stated Standard

Now the step becomes a model call and the goal becomes a judgement. The package's `judged` helper wraps next chapter's judge into a goal function: give it criteria in words and a threshold score, and it returns the `goal(state)` check `run_loop` wants. Reading Chapter 11 first is allowed and even sensible; the wiring makes sense on contact either way.

```python
# Listing 10.2 of 3: improve until good enough (improve_paragraph.py)
from hands_on_ai.chat import get_response
from hands_on_ai.loop import judged, run_loop

result = run_loop(
    step=lambda draft: get_response(f"Improve this paragraph:\n{draft}"),
    goal=judged("clear, concise, and friendly", threshold=4),
    start="loops are when you do stuff again and again",
    max_iters=5,
)

print(result["result"])
print("in", result["iterations"], "iterations; goal met:", result["met_goal"])
for draft in result["history"]:
    print("-", draft)
Count the model calls before you run it, because Chapter 3's arithmetic has a new multiplier. Each iteration costs one improvement call from the step and one judging call hidden inside the goal, so a budget of five iterations is up to ten calls, each carrying its own prompt. On a local model that costs patience; on a metered provider it is a line item, and `max_iters` is where you signed for it.

Read the printed history with a marker in hand. A draft may reach the threshold by becoming shorter in a way that loses the point, because "concise" was in your criteria and "keeps the original meaning" was not. A later iteration may be worse than an earlier one, and here `run_loop` has a character trait you must know: it keeps the last state, whatever the history shows. The goal check happens after the step, so a run that decays through its final iteration returns the decayed text with `met_goal` honestly false, and the best draft of the run sits in `history` for you to rescue by hand. That design is simple and sometimes wrong, which is why the package ships a second shape.

## The Ratchet: Keep Only Wins

`run_ratchet` changes what the loop remembers. Each iteration, the step proposes one change to the current best. A `score` function rates the proposal, and the proposal replaces the best only if it scores strictly higher. Otherwise it is discarded, the way a mechanical ratchet refuses to slip backward, and the loop logs every proposal's score and whether it was kept. The package nicknames it the Ralph Wiggum technique, and the loop it describes is a classroom-sized relative of how optimisation harnesses grind on a problem overnight.

```python
# Listing 10.3 of 3: only improvements survive (ratchet_paragraph.py)
from hands_on_ai.chat import get_response
from hands_on_ai.eval import judge
from hands_on_ai.loop import run_ratchet

CRITERIA = "clear, concise, friendly, and keeps the original meaning"

result = run_ratchet(
    step=lambda draft: get_response(
        f"Improve this paragraph in one small way:\n{draft}"
    ),
    score=lambda draft: judge(draft, CRITERIA)["score"],
    start="loops are when you do stuff again and again",
    max_iters=5,
)

print(result["best"])
print("final score:", result["score"])
for row in result["log"]:
    print(row)

Each row of the log is one proposal: its iteration number, its score, and whether it was kept. A healthy log shows a few keeps early and discards later as the text firms up. A log of all discards says your starting text already beat everything the step proposed, or that the score cannot tell your proposals apart. A log of all keeps with climbing scores on a vague criterion should make you suspicious in the other direction: the step may be learning to please the scorer rather than to serve the reader. Note two bookkeeping facts for your budget: the ratchet scores the starting state once to set the baseline, and a proposal whose score comes back `None`, which happens when a judge's reply cannot be parsed, is never kept. Inaction on unreadable evidence is the right default.

The two shapes differ in what a mediocre run hands back. `run_loop` pursues a stated standard and returns wherever it stopped, with the history as evidence. `run_ratchet` guarantees the returned text is at least as good, by your score, as where you started, and pays for the guarantee with a scoring call per proposal and a step that must be kept to small changes. For a paragraph, the ratchet's guarantee is worth it. For reaching a format or passing a test, the plain loop reports failure faster.

A step and a goal that are each slightly wrong do not cancel out in a loop. They compound. A step that pads text and a goal that rewards thorough-sounding criteria will march a paragraph away from its reader a few confident iterations at a time, logging progress at every step. Read histories and logs, especially early on, the way Chapter 9 taught you to read stage outputs. The budget you set is also a statement about how far you trust the amplifier unsupervised.

## Where a Demo Can Mislead You

"It refines itself until it is excellent" compresses every question in this chapter into a slogan. What is the goal, stated so a third party could check it, and who wrote the criteria? What is the budget in iterations and in model calls, and what does the system return when the budget expires without the goal firing? Does it keep the last attempt or the best? May I see a history or a log from a run that failed to meet its goal, since anyone can show the run that converged?

## Chapter Summary

- A goal loop alternates a `step(state)` doing one piece of work with a `goal(state)` check stated in advance, bounded by `max_iters`.
- `run_loop` returns the final state, the iteration count, whether the goal was met, and the full history. It keeps the last state even when the goal never fires.
- `judged(criteria, threshold)` turns the model-as-judge into a goal. Each judged iteration costs one step call plus one judging call.
- `run_ratchet` keeps a proposal only when it scores above the best so far, logs every proposal with its score and keep decision, and never keeps an unscorable proposal.
- Loops amplify the step and the goal together. Histories and ratchet logs are how you watch direction as well as arrival.

# The Judge 

> When output is cheap and plentiful, the scarce skill is telling good from fluent, at a scale your eyes cannot cover alone.

Package companion: `hands_on_ai.eval`, the `judge` function behind Chapter 10's goals. Listings checked against `hands-on-ai` 0.6.0.

Misconception this chapter kills: "I can eyeball quality." At scale you cannot, the demo is not a test, and a score is a signal to calibrate rather than a verdict to obey.

The build: `judge-your-bot`, the package's evaluation project. Score a set of chatbot answers against stated criteria, then compare the judge's marks with your own and read the disagreements closely.

Python you need: dictionaries and loops from .

## The Concept First

Every chapter since Chapter 5 has widened the gap this one addresses. Production is now the cheap direction: a call produces an answer, a pipeline produces a draft, a loop produces five drafts and a log. Evaluation is where the cost now sits: somebody, or something, has to read all of that output and separate the sound from the merely fluent, and a human reader does not scale past a few dozen items a day with their attention intact. The industry's working answer is the pattern this chapter takes apart: LLM-as-judge, in which a model is asked to score an output against criteria you state, returning a number and a reason your code can act on, as Chapter 10's goals already did.

The judge is the smallest build in the book. It is one call, with a system prompt casting the model as a strict but fair evaluator and demanding exactly two lines back, a score and a reasoning, followed by a small parser that extracts the number and clamps it into the scale. There is no special evaluation engine, which is why calibration matters more than the mechanism: a judge is a model producing text about text, with a model's failure modes, and the craft is in knowing how far its numbers track your own judgement on work you have actually read.

Judging is becoming a baseline skill of working with AI in the way estimating a search result's reliability became one a generation ago, because output volume has already passed the point where unaided reading is the control. At scale, the alternative to a calibrated judge is no review, with a demo's confidence in its place.

## Understanding Through Real Life

Think of examination marking at scale. One chief examiner cannot read ten thousand scripts, so a team of markers works from a shared rubric: criteria bands, exemplar answers at each level, and moderation meetings where markers compare scores on the same scripts and argue until their standards converge. Examination boards do not treat a new marker's first hundred marks as ground truth; those marks are sampled, compared, and adjusted. Trust in a marker is earned per rubric, per season, and it expires when the rubric changes.

An LLM judge joins your marking team as an indefatigable new marker who reads at inhuman speed and never gets tired at script nine thousand. It also arrives with no stake in being right, a susceptibility to confident presentation it inherited from training, and standards that live entirely in the rubric text you handed it. The moderation meeting is the process by which this particular marker, on this particular rubric, earns the right to mark unsampled work. This chapter's build is that meeting, held at classroom scale with your own marks as the comparison.

## The Build: Put the Judge on the Bench

Start with a single verdict, printed in full, so every part of the return value is visible:

```python
# Listing 11.1 of 2: one verdict, all its parts (one_verdict.py)
from hands_on_ai.eval import judge

verdict = judge(
    "TCP retransmits lost packets so data arrives complete and in order.",
    criteria="accurate, concise, and answers the question asked",
    question="What does TCP do?",
)

print(verdict["score"])
print(verdict["reasoning"])
print(repr(verdict["raw"]))
The dictionary has three entries. `score` is the parsed number, an integer on the scale you chose (1 to 5 unless you pass `scale=`), or `None` when the reply contained no readable score. `reasoning` is the one-sentence justification the prompt demanded. `raw` is the judge's untouched reply, kept so that when a score surprises you, the text it was parsed from is one print away. Keep `raw` in anything you build on this.

Run the listing a few times on the same answer, and treat the wobble as data. Scores may hold steady or drift by a point between runs, because the judge is a model call, subject to everything Part I taught you about model calls. Drift does not make the instrument useless, any more than marker variance abolishes examinations. It tells you what the numbers can and cannot carry: separating a 2 from a 5 with confidence, perhaps, while a ranking built on 4-versus-5 distinctions is reading tea leaves unless your calibration says otherwise.

## The Moderation Meeting: Judge Your Bot

Now the project the package names `judge-your-bot`. Take a small set of answers from a bot you have built, a personality bot from Chapter 2 or your RAG bot from Chapter 6 answering questions you chose, and mark them twice: once yourself, once with the judge, against the same written criteria.

```python
# Listing 11.2 of 2: your marks beside the judge's (judge_your_bot.py)
from hands_on_ai.eval import judge

CRITERIA = "accurate, based only on the provided documents, and concise"

cases = [
    ("What does TCP do?", "TCP retransmits lost packets so data arrives complete and in order.", 5),
    ("What does TCP do?", "TCP is a very important protocol that does many things on the internet.", 2),
    ("How does HTTP work?", "The rules do not say.", 4),
]

for question, answer, my_score in cases:
    verdict = judge(answer, CRITERIA, question=question)
    print(f"mine={my_score} judge={verdict['score']} :: {verdict['reasoning']}")

Write your scores into the listing before you run it, from your own reading, as the tuples above suggest. Then read the output disagreement first, agreement second. Each mismatch is a small investigation with exactly three possible findings. Your criteria may be underwritten: the judge marked to the words you gave it, and the words did not say what you meant, which is Chapter 2's instruction lesson in a new uniform. Your own mark may be the sloppy one, given on a skim the judge's slower pass exposed. Or the judge may simply be wrong in a way worth characterising: rewarding length, rewarding confidence, missing a factual error it had no source to check against, punishing a correct refusal because it looks unhelpful. Sort your mismatches into those three piles and you have a calibration record: where this judge, on this rubric, with this model, can be trusted, and where it must be sampled or overruled. Refresh that record when the model or criteria change.

## Writing Criteria a Judge Can Use

Rubric writing for a model follows the instruction rules from earlier chapters. Criteria should name checkable properties rather than vibes: "states the borrowing limit as a number" can be marked against a document; "high quality" cannot be marked against anything. Where correctness matters, give the judge something to be correct against: the question, the source chunk, the expected fact. A judge asked to score accuracy from its own training is a second opinion from the same well the first answer was drawn from, and Chapter 5 already told you what that well contains. Keep the scale honest about the discrimination you verified in moderation: if your judge reliably separates poor, adequate, and strong, a 1-to-3 scale collects the information without pretending to five points of it. And separate criteria that pull against each other into separate judgements when the trade-off matters, because a single score for "accurate and entertaining" hides which one failed, as Chapter 2's contradictory system prompts hid which instruction the model disobeyed.

The parser clamps and fails visibly, by design. A judge that replies with a score off the scale has it clamped to the nearest end. A judge whose reply contains no `SCORE:` line yields `None`, which Chapter 10's goal treats as not good enough and the ratchet treats as never an improvement. Neither behaviour fixes a confused judge, but both keep one from silently passing work.

A judge reads the output it is marking, and that output is model-generated text, which can contain sentences addressed to the marker: flattery, instructions, a forged `SCORE: 5` line of its own. The parser takes the first score it finds in the judge's reply, and a small model quoted its input often enough for this to matter in adversarial settings. In your classroom builds the risk is mostly accidental, but the bench rule from Chapter 7 applies with roles reversed: treat the marked text as untrusted input to the marking process, and be suspicious of perfect scores on work you have not sampled.

## Where a Demo Can Mislead You

Ask the moderation questions of any evaluation claim, however scientific its percentages, benchmark names, and charts look. Who or what produced these scores, against criteria I may read? Where is the calibration sample comparing the judge's marks with marks from someone accountable, and what did the disagreements look like? What happens to the score distribution when the judge model and the judged model swap? Can I see raw verdicts, or only the averaged number that survived contact with a slide template? These questions ask whether the vendor held the moderation meeting and can show its minutes.

## Chapter Summary

- The judge is one model call with a strict evaluator prompt and a parser. It returns `score` (clamped to the scale, or `None` when unparsable), `reasoning`, and the untouched `raw` reply.
- Scores wobble between runs and track your rubric's wording as much as the work's quality. Calibration against your own marks on sampled work is what converts scores into a usable signal.
- Disagreements sort into rubric gaps, your own marking errors, and judge errors such as rewarding length or confidence. Each pile has a different fix.
- Checkable criteria, evidence supplied to the judge, a scale sized to verified discrimination, and separate scores for competing virtues all raise what the numbers can carry.
- Marked text is untrusted input to the marking process. Keep raw verdicts, sample continuously, and treat averages without minutes as marketing.

# Typed Answers 

> Most programs do not need paragraphs from a model. They need one option chosen, one yes or no, one score, one record, in a shape code can trust.

Package companion: `hands_on_ai.decide` (`classify`, `decide`, `score_output`, `extract`). Listings checked against the `decide` module on `hands-on-ai` main, after 0.6.0; install from the repository until it ships in a release.

Misconception this chapter kills: "The model replies in prose, so my program must parse prose." You can ask for small typed judgments instead, and validate the shape before your code believes a word of it.

The build: a support-ticket router and a refund decider, run first on your local model, then on a hosted System One model if you have a key, with marks compared.

Python you need: dictionaries and one small class definition for extraction, both met in . The class here is data-shaped only: field names and types, no behaviour.

## The Concept First

Chapter 11's judge smuggled a new kind of call into the book. It wanted one integer and one sentence, and dug them out of the reply with a regular expression, hoping the model kept the format. Chapter 7's agent wanted the same kind of smallness: a tool name and an input string, not a meditation. A large share of what programs actually need from models has that shape. Which queue does this ticket belong to? Does this message ask for a refund? How frustrated is this customer, on a stated scale? What are the name, date, and total on this invoice? Questions with small, known answer spaces, asked thousands of times, where a paragraph of prose becomes a parsing problem.

TypeSafe gave a name and a service to this end of the trade: System One models, after Kahneman's fast, intuitive System 1, which return typed decisions and probabilities through three primitives. Choice picks one option from a set you define. Noul answers a yes/no question as a probability. Score rates something along ordered levels you describe. Their model, Jev, returns calibrated judgments your code can compose, without chat or explanations. You do not need their service to learn the pattern, because an ordinary chat model constrained to a schema can play the same role in miniature, which is what the package's `decide` module does. What the hosted model adds is calibration: probabilities trained to mean what they say across many predictions.

Schema constraining guarantees the shape of the answer. It says nothing about whether the answer, or its self-reported confidence, is right. A local model asked for a confidence will produce a number in range with the same fluency it produces everything else. Chapter 11's moderation habits therefore apply to every number in this chapter: calibrate on cases you marked yourself, or treat the number as decoration.

## Understanding Through Real Life

Think of the difference between asking a colleague to "look into this customer email" and handing them a triage slip. The slip has boxes: department (tick one of three), refund requested (yes or no), urgency (circle 1 to 5), account number (write it here). The slip is more useful to everything downstream than the conversation, because the routing rule, the queue, and the report at the end of the week all consume boxes. Nobody asks the slip to explain the customer's feelings at length; there are other instruments for that, slower ones, reached for when the boxes say this case deserves them.

Fast typed judgments handle the bulk and the routine. Measured uncertainty routes the remainder to a person or to a slower reasoning model, the System 2 end of the shop. Most of this book has been about the slow end. Being fast takes narrow questions, defined answer spaces, and evidence that the fast answers deserve the trust your thresholds place in them.

## The Build: a Router and a Decider

The module's four functions share one interface habit with the rest of the package: they return plain dictionaries and never raise for a model-side failure, putting `None` in the answer fields with an explanation under `error`. Start with Choice, wearing its package name, `classify`:

```python
# Listing 12.1 of 3: route the ticket (route_ticket.py)
from hands_on_ai.decide import classify, decide

ticket = "Help! My payouts have been failing for 3 days and I want my money back."

routed = classify(
    ticket,
    options=["billing", "technical", "sales"],
    instructions="Which team should handle this ticket?",
)
print(routed["choice"], routed["confidence"], routed["error"])

refund = decide(ticket, "Does this message request a refund?")
print(refund["answer"], refund["probability"], refund["error"])
Run it on tickets of your own invention, including awkward edge cases: a technical fault that mentions money, a billing question caused by a bug, a message that fits no box at all. The option list is a closed world: the function validates the reply against it and hands back `None` rather than an invented department, so an "other" option is yours to include or to live without. "Which team should handle this?" plus three bare labels asks the model to guess your org chart; adding one line of rubric per option, the way TypeSafe's own examples pair each choice with a description, turns guessing into marking. Chapter 2's instruction craft and Chapter 11's rubric craft are the same craft here, applied to a smaller answer.

The extraction primitive has no System One counterpart, because Jev judges rather than transcribes, but it belongs in the same drawer: a typed record out of messy text, validated field by field:

```python
# Listing 12.2 of 3: a record out of prose (extract_invoice.py)
from pydantic import BaseModel

from hands_on_ai.decide import extract

class Invoice(BaseModel):
    vendor: str
    total_dollars: float
    due_date: str

result = extract(
    "Invoice from Sunrise Catering. Total due: $1,240.50. "
    "Please pay by 14 November 2026. Thank you for your business.",
    Invoice,
)
print(result["data"])
print(result["error"])

The `Invoice` class is a schema in Python syntax, with three field names and three types. Underneath, the local backend hands that schema to the model through Instructor's JSON-schema mode, the same machinery Chapter 7's JSON agent format used to validate tool calls before anything ran. What comes back has been checked against the schema by construction, so `total_dollars` is a number your code can add up, not the string `"$1,240.50"` waiting to break a sum. Fields the text cannot support are the interesting failure: try an invoice with no due date and read what the model does with its instruction to leave a field empty rather than invent one. Then decide, as a designer, whether empty, invented, or refused is the failure your system can afford, because the schema guarantees shape only.

## The Same Judgments, Calibrated

Swap the backend and the interface holds while the meaning of the numbers changes. With a TypeSafe key in `TYPESAFE_API_KEY`, the same two calls go to Jev:

Without a key, the Jev row prints its error in plain sight and the local row carries the run, which is the correct classroom default. With one, compare more than the answers. Jev's Choice returns a probability for every option, summing to one, and its Noul probability is the product being sold: trained so that across many predictions, cases scored near 0.8 come out yes about eighty percent of the time. Your local model's confidence is a number it generated because the schema had a slot for one. On a single ticket both may look identical. Across fifty tickets you marked yourself, in Chapter 11's moderation style, the difference becomes measurable: bin each backend's probabilities and check the bins against reality.

Cost belongs in the same comparison, because these primitives exist to run at volume. A routed ticket locally is one small call on hardware you own. Jev is priced per input token at rates that make a million triage calls a rounding error next to one misrouted enterprise ticket, and it evaluates many questions against one state in a single request. Neither fact decides the architecture on its own; together with your calibration table, they might.

Chapter 11's `judge` now tries this chapter's typed scorer first and falls back to its old two-line text format only when the structured call cannot produce a score. Its return shape, `{score, reasoning, raw}`, did not change, and Chapter 10's loops never noticed. That is the pattern to copy in your own systems: typed path preferred, text path as the documented fallback, the interface above both untouched.

## When Fast Is the Wrong Instrument

For every question in this chapter there is a neighbouring question the primitives serve badly. Typed judgments do not explain, negotiate, draft, or reason through novelty; a Choice among three departments cannot tell you the ticket describes a fourth problem your org chart lacks. They do not fetch evidence; a refund decision made without the transactions and the policy in the state is a bare question from Chapter 5 with a probability attached. And their speed creates a specific organisational temptation, to let thresholds quietly become policy: auto-refund below this probability, auto-reject above that score. Thresholds are decisions about who bears the cost of the fast lane's errors. They deserve the same daylight as any other policy, set from your calibration data and revisited when the model or the mix of cases changes.

Used inside their fence, though, typed answers change what the rest of the book's machinery costs. A router decides which retrieval index a question deserves before Chapter 6 spends its tokens. An extractor turns incoming prose into fields Chapter 9's pipeline can file without a model rereading it at every stage. A decider gates Chapter 10's loop with a cheap check before an expensive judge wakes.

## Chapter Summary

- Typed primitives give programs small answers in validated shapes: `classify` picks one option, `decide` returns a yes/no probability, `score_output` rates against criteria, `extract` pulls a typed record from prose.
- The local backend constrains an ordinary model to a Pydantic schema: shape guaranteed, confidence self-reported and uncalibrated. Jev's hosted System One backend sells calibrated probabilities behind the same interface.
- Failures arrive as `None` fields with an `error`, never as exceptions or invented options; closed option lists make "other" a design decision.
- Calibration is a table you build from your own marked cases, per backend, per question. Without it, confidence is decoration and thresholds are policy by accident.
- Typed answers compose: routers before retrieval, extractors before pipelines, cheap deciders before expensive judges, escalation where uncertainty concentrates.

# Pictures 

> Seeing, in this machinery, is a prompt with a picture attached. The reply is still text, and it can still be wrong in a confident voice.

Package companion: `hands_on_ai.vision`, its one function `describe`. Listings checked against `hands-on-ai` 0.6.0.

Misconception this chapter kills: "Vision is a different kind of AI." Images go into the same kind of call, and descriptions come out.

The build: `talking-picture`, the package's vision project. A photograph that answers questions about itself, asked three different ways.

Python you need: one function call and a file path. The interesting work in this chapter is choosing photographs that test the model honestly.

## The Concept First

A vision-language model, VLM for short, accepts a payload whose user message carries two parts instead of one string: your text question, and an image. Somewhere inside the server, the image is converted into tokens, the same internal units the model uses for words, and the machinery from Chapter 1 proceeds as always. Text and a picture go in, and text comes out. The module docstring puts it plainly: seeing is another way of writing a prompt. This module describes images. It does not create them; image generation is a different family of models and outside this book.

How the image travels explains the costs and failures to come. A web address can pass through as a link for the server to fetch. A local file, the normal case for your own photographs, is read by your code and encoded as base64, a text representation of the file's bytes, inlined into the payload as a data URL. Your photograph becomes a long string inside the JSON from Chapter 1: a phone photograph inflates into hundreds of thousands of characters of payload before the server has done any thinking, which is one reason vision calls are slower and the package allows them a generous timeout.

## Understanding Through Real Life

Think of describing a scene over the phone to someone who has never seen your street. The description is a translation, and like every translation it is shaped by the question asked. "What is happening in this photo?" earns a story about the scene. "How many people are wearing hats?" earns a count the describer may or may not have performed carefully. "What does the sign say?" earns a reading, accurate where the sign is legible and confabulated where it is not, unless the describer is the rare sort who says the text is too small to read.

A VLM is that describer with two exaggerations. It has seen vastly more photographs in training than any person, and its scene sense is correspondingly strong. And it shares the language model's reluctance to say it cannot tell: fine print, exact counts, small text, spatial relations like left-of versus behind, and anything the downscaled encoding smeared away may all come back rendered in fluent certainty. Chapter 5's rule applies unchanged, with pixels added: separate what the image could show from what this call could recover, and check the parts that matter against the picture yourself.

## Connect a Vision Model Before You Build

Vision needs a model that accepts images, configured separately from your chat model, the way Chapter 6 added an embedding model. The default is `moondream`, a small vision model, changeable through the `vision_model` setting or `HANDS_ON_AI_VISION_MODEL`:

python
# Listing 13.1 of 2: the talking picture (talking_picture.py)
from hands_on_ai.vision import describe

photo = "market.jpg"

print(describe(photo))
print(describe(photo, "What is the main thing being sold here?"))
print(describe(photo, "How many people are in this picture? Count carefully."))

The first call uses the default prompt, "Describe this image.", and gets you the tour. The second shows the usual pattern: questions put to a picture, such as reading a label, identifying a plant, checking whether a gauge is in the red, or asking what is funny here. A picture plus a pointed question is the vision equivalent of Chapter 5's grounded prompt, with the image as the evidence in the room. The third call is the honesty test. Counting is where small vision models go to be humbled, along with small text and precise spatial claims, and your own model may produce a crisp number you can refute by looking at the photograph.

Underneath, `describe` assembles the two-part user message and sends it through the same `chat_completion` machinery as every chat call in the book, with the longer timeout. One behaviour will look familiar from Chapter 1 by design: point it at a file that does not exist and you get an error string back, `❌ Error: Image file not found: ...`, rather than a crash. Your program can tell failure from description the way it learned to in Part I.

## What It Can and Cannot See

A useful first hour with a VLM sorts its answers into three piles. Scene gist is strong: what kind of place this is, what is broadly happening, the salient objects and their rough relations. Reading is conditional: signage and labels come back well when they are large, level, and high-contrast, and degrade into plausible invention as they shrink, tilt, or blur. Precision work is weak on small models especially: exact counts, small differences between similar objects, charts read to values, and anything depending on detail the encoding downscaled away. Results vary with model size, and re-sorting the piles per model is the same moderation exercise Chapter 11 taught, with the photograph as ground truth sitting right there.

Vision output is text, so it can be judged: a description can be scored against criteria, and better, against a human transcript of the same image, by the machinery of Chapter 11. And a picture rarely answers the question behind the question alone. What the sign says comes from the photograph; whether the shop is open now comes from a document or a tool. Systems that pair a VLM's description with retrieval from Chapter 6 or a lookup tool from Chapter 7 combine this book's parts on one bench.

Your photographs will be uploaded, encoded, to whatever server your configuration names, and Chapter 3's transcript warning applies with faces in place of words. Local models keep the bytes on your machine; hosted ones are governed by the provider's retention terms. Photographs of other people deserve the consent habit you would want applied to your own likeness, and some workplaces and jurisdictions regulate biometric uses well beyond anything in this chapter. Description for learning is benign. Build the consent reflex anyway, while the stakes are homework.

## Where a Demo Can Mislead You

Vision demos choose photographs the way Chapter 5's demonstrators chose questions: big subjects, clean light, legible signs, counts of three. The counter-demo takes a minute to assemble from your own phone. A crowd to count, a receipt to read to the cent, a dashboard at an angle, a shelf where one item differs from its neighbours. # Voice 

> A voice agent is the chat loop with ears and a mouth bolted on: speech in, text through the machinery you know, speech out.

Package companion: `hands_on_ai.voice`, with `transcribe` and `speak`, around the `Conversation` from Chapter 3. Listings checked against `hands-on-ai` 0.6.0.

Misconception this chapter kills: "Voice AI is a different technology." It is transcribe, think, speak: three plain calls, and a fight against the clock.

The build: a talk-out-loud chatbot in two forms: typed input with spoken replies first, then a recorded question carried the whole way around the loop.

Python you need: function calls and the `Conversation` object. The new material is about servers and timing, not syntax.

## The Concept First

The thinking in a voice system is the text machinery of Parts I to IV, unchanged, with two translators at the edges. A speech-to-text model, STT, takes an audio file and returns the words as text. That text enters the chat loop you built in Chapter 3 and receives a reply in text. A text-to-speech model, TTS, takes the reply and returns an audio file. That gives the loop: transcribe, think, speak. Each translator is a model call to an OpenAI-compatible endpoint under `/v1/audio/`, made with the same client patterns as Chapter 1 and Chapter 6's embeddings. Voice adds senses the way pictures did: by converting to and from the text the system already runs on.

What changes is the constraint. Text chats tolerate a slow reply gracefully; the words appear when they appear. Spoken conversation runs on human turn-taking clock, where a pause of two seconds already feels like the other party has wandered off. Every hop in the chain spends from that budget: recording and uploading the audio, transcribing it, thinking over a growing transcript, synthesising the reply, downloading and playing it. Latency, the total time from the end of your sentence to the start of the reply, is the engineering problem of voice systems.

## Understanding Through Real Life

Think of a conversation conducted through two interpreters in a soundproof booth relay. You speak your language. The first interpreter renders it into the booth's working language and passes the words across. Your counterpart, who thinks in the working language, composes a reply. The second interpreter renders the reply back into yours. Everyone in the chain can be excellent and the conversation can still feel drunk, because each hand-off adds delay and small translation choices: a name heard slightly wrong enters the working language as fact, and a long, clause-heavy reply that reads beautifully becomes punishing when someone has to speak it and someone else has to stand there listening.

Transcription errors propagate inward disguised as the user's own words, and the system answers the sentence it heard rather than the one you said. Reply style propagates outward: length, lists, tables, and URLs that serve a reader well become unusable when spoken, which is why voice system prompts beg for brevity.

## Two More Servers Before You Build

Audio models usually do not live on the chat server. A plain Ollama install serves chat, embeddings, and vision, but speech typically comes from a separate local server that speaks the same `/v1/audio/` dialect: tools such as speaches or whisper.cpp serving Whisper models for transcription, and Kokoro or Piper for synthesis. The package therefore carries separate settings, `HANDS_ON_AI_STT_SERVER` and `HANDS_ON_AI_TTS_SERVER`, which default to your main server, and separate model settings defaulting to `whisper-1` for transcription and `kokoro` for speech. A hosted provider with audio endpoints collapses all of this back to one address and one key, at hosted prices and with your voice recordings travelling to it.

Before building anything, point those settings at servers you actually have, local or hosted, and confirm with the doctor habits from Chapter 4.  collects the variables in one table. Then test the two translators in isolation, in the spirit of Chapter 7's call-the-tool-yourself rule:

```python
# Listing 14.1 of 2: the ears and the mouth, separately (voice_pieces.py)
from hands_on_ai.voice import speak, transcribe

print(speak("The loop is transcribe, think, and speak.", out_path="hello.wav"))
print(transcribe("hello.wav"))
`speak` returns the path of the WAV file it wrote, `speech.wav` in the current folder if you do not name one, or the familiar error string in place of the path. Empty text comes back as a warning string without troubling any server, Chapter 1 manners again. Feed the file it just made back through `transcribe` and you have run a small experiment: a sentence that went text to speech to text, with both translators at their best behaviour, on clean synthesised audio. Compare the returned words with the originals. Then transcribe a recording of yourself, made on your phone in a real room, and compare again. No chat model downstream can recover words the transcription missed.

## The Build: the Loop Wearing Headphones

The package's own interactive voice loop starts with a sensible cheat: you type what you would say, and only the reply is spoken. Microphone capture is platform plumbing, left as an extension exercise. In your own code it is Chapter 3's `Conversation` with one added line, plus a system prompt that knows its output will be heard rather than read:

```python
# Listing 14.2 of 2: typed question, spoken answer (voice_chat.py)
from hands_on_ai.chat import Conversation
from hands_on_ai.voice import speak

SYSTEM = (
    "You are a helpful assistant. Keep your answers short and "
    "conversational, one or two sentences, because they will be read aloud."
)

chat = Conversation(system=SYSTEM)

question = transcribe("my_question.wav") if False else input("You: ")
reply = chat.ask(question)
print(reply)
print(speak(reply, out_path="reply.wav"))

Flip the `if False`, record your question as a WAV file by whatever tool your machine offers, and the same script runs the full round trip, ears included, with `Conversation` still holding the transcript between turns if you wrap it in a loop of your own. Playback of the reply file is deliberately your problem; the package's command-line REPL makes a best effort with `afplay` on macOS and `aplay` on Linux and otherwise tells you to open the file. That seam, getting sound out of speakers and in from microphones across operating systems and browsers, is where small demos end and voice frameworks like Pipecat begin, and  points at the bridge project, the package's Build the World's Smallest Pipecat.

Time one full turn with a stopwatch: question finished, reply audible. Then ask where the seconds went. Transcription of a short clip, the chat call over a transcript that grows every turn (Chapter 3's tax, now audible), synthesis of the whole reply before the first sound plays. The industry's answers are all visible from here: stream the reply in pieces and start speaking the first sentence while the rest generates, keep spoken answers short by instruction, run smaller local models for the translators, and put the servers close. None of those change the shape; they shorten the relay.

A voice recording identifies a person in ways a typed sentence does not, and speech synthesis can be pointed at imitation with enough samples. The consent reflex from Chapter 13 applies in full: record yourself freely, record others with their knowledge, know which server your audio travelled to, and treat cloning a real person's voice as a line that needs their explicit agreement rather than your technical ability. The tools in this chapter synthesise a stock voice. Keep the ethics at stock settings too.

## Where a Demo Can Mislead You

Voice demos are staged in quiet rooms with close microphones, short questions, and presenters who have learned to pause where the demo needs them to. Your counter-demo is a kitchen with a kettle on, a name the transcriber will mangle, a question whose honest answer is a list, and an interruption mid-reply. What is the end-to-end latency at the ninety-fifth percentile, not the anecdote? Where does my audio go, how long is it kept, and is it used for training? What happens when transcription hears me wrong: can I see the words the system thinks I said and correct them before action is taken? And which parts of this are your engineering, versus three API calls I assembled this morning from a learning package?

# The Older AI in the Room 

> Before the chat box, and still underneath much of the world, sit models fitted to tables of numbers. They are fast, inspectable, and frequently the right tool.

Notebook companion: `classical_ml.ipynb` in the package repository's `notebooks/` folder. It needs only scikit-learn, already installed as a package dependency, and runs in seconds with no model server of any kind.

Parts I to V needed no training and almost no maths. This optional part relaxes both, in notebooks, at toy scale. It begins with the classical machine learning that predates LLMs, because the training chapters after it reuse its habits (features, splits, sealed tests) at every step. Skip the whole part and the book remains complete; read it and the title's umbrella word, AI, is one you have personally surveyed rather than taken on trust.

Misconception this chapter kills: "AI means LLMs now." The field is older and wider, and for a large class of tabular problems the older machinery is cheaper, clearer, and better behaved than a language model will ever be.

The build: a decision tree classifying iris flowers from four measurements, read back as plain rules and scored on sealed rows; then the labels thrown away and k-means left to find the groups alone.

## The Concept First

AI is the umbrella: machines doing tasks we would call intelligent in a person. Under it sit several families with different ancestries. Symbolic AI reasons over rules and search. Classical machine learning fits models to tables: rows of examples, columns of numeric features, and, for supervised learning, a label to predict. Deep learning fits neural networks with gradient descent, the machinery the next chapter opens, and gave us both convolutional networks (CNNs) that learned to see images as spatial patterns and, eventually, the transformers behind LLMs. The first five parts of this book lived in that last twig of the family tree. This chapter visits the trunk it grew from, because the trunk still carries enormous weight: spam filtering, fraud scoring, demand forecasting, medical risk scores, and recommendation plumbing run overwhelmingly on classical models and their ensembles, as the 150-flower example below shows.

The classical workflow follows a rhythm: assemble a table, seal some rows away for testing before any fitting begins, fit a model on the rest, predict on the sealed rows, and evaluate against the truth you withheld: `fit`, `predict`, `evaluate`. Every later chapter in this part, including the adapter work with its sealed eval set, is that rhythm at greater expense.

## Understanding Through Real Life

Think of a botanist's field key, the printed kind that walks you through a plant by measurements. If the petal is under two and a half centimetres, it is a setosa; otherwise check the width; otherwise check this. A good key is a decision tree written by a person over seasons of observation. The notebook's first build asks what key the data writes for itself when an algorithm chooses the thresholds to best separate the rows it was shown. The second build removes the guide's species labels entirely and asks a different field question: given only measurements, do these flowers fall into natural groups at all? That is clustering, and its ancestor is every market segmentation and anomaly hunt running quietly in industry: find the lumps in the data first, argue about their names second.

## The Build: a Key the Data Writes Itself

Open `classical_ml.ipynb` and run it top to bottom; this section narrates what to look at. The dataset is the iris table that ships inside scikit-learn, so nothing downloads: 150 flowers, four measurements each, three species in equal numbers. Thirty percent of rows are sealed away stratified by species, leaving 105 training rows and 45 test rows. Fitting is one line, `DecisionTreeClassifier(...).fit(X_train, y_train)`, and it is over before you can look up. After five parts of server round trips, token budgets, and timeouts, a model that trains in milliseconds on your own CPU and needs no account, key, or network is a useful reminder that "AI" did not always imply a data centre.

Then print the model. The learned key opens with the same observation a botanist would, that petal length alone separates setosa cleanly (`petal length (cm) <= 2.45`), and resolves the harder two species through a handful of further width thresholds, eight leaves deep at most. Every prediction the tree ever makes can be traced down those branches by a person with a ruler. Scored on the sealed rows, the run captured for this draft (seed fixed, so yours should match) reaches 0.933 accuracy: 42 of 45 correct, with all three mistakes calling borderline versicolor flowers virginica. Read the mistakes individually, as the notebook does. Their measurements sit where the two species genuinely overlap, which is a property of flowers rather than a scandal in the model, and deciding whether those three errors matter is a judgement no accuracy number makes for you, as Chapter 11's moderation sessions also show.

The second build deletes the answer key. K-means is asked for three clusters in the same measurement space, knowing nothing of species: pick three centres, assign each flower to the nearest, move each centre to the middle of its assignees, repeat until settled. Against the true species it scores an adjusted Rand index of 0.73 in the captured run, where 1.0 is perfect agreement and 0 is chance. The composition table explains the decimal: one cluster is purely setosa, all fifty, the geometry having found unaided what the tree's first threshold found with labels; the other two clusters split the versicolor and virginica ranges untidily between them, because those species really do blur into each other in these measurements. Unsupervised evaluation argues from structure and usefulness rather than from a withheld answer key, a softer standard that the next chapter's sealed losses will stiffen again.

## What Each Branch Is For

The visit teaches a routing skill, of the same kind Chapter 12 fenced around typed judgments: given a problem, which branch of the family earns the first attempt?

| Your material looks like | Reach first for | Because |
|---|---|---|
| A table of numbers, a label to predict | Decision tree or its ensembles; SVM beside it | Fast, inspectable, strong baselines, honest error bars |
| A table of numbers, no labels | k-means and kin | Structure and segments before anyone names them |
| Images, audio, signals with spatial or time shape | CNNs and deep nets (next chapter's family) | Features must be learned from the raw grid, not hand-slotted |
| Language, instructions, messy documents, conversation | LLMs and this book's wrappers | Meaning arrives unslotted; that is their whole trick |

A support vector machine, the SVM in the first row, earns its mention as the classical classifier that draws the widest separating boundary it can between classes, the geometric opposite temperament to a tree's axis-aligned questions; the notebook's closing cell swaps it in on identical splits so you can compare held-out scores rather than temperaments in the abstract. Ensembles, forests of trees voting, are why the first row still wins tabular competitions against far larger machinery. The routing cuts both ways. Reaching for a language model to classify rows that already sit in clean numeric columns is usually an expensive way to get a worse, less inspectable answer. Conversely, hand-engineering feature columns for raw text is the 2010s version of the same mistake.

## Where a Demo Can Mislead You

Two symmetrical cons run in this territory. The first relabels: a logistic regression or a gradient-boosted tree that has scored transactions well for a decade is presented, post-2023, as "our AI platform", with the LLM era's glamour borrowed for machinery that neither needs nor survives it. The second overreaches: an LLM demo classifies support tickets from raw text beautifully, and nobody mentions the tree over structured fields that would do most of the same job at a thousandth of the cost with rules a regulator can read. What model family is this, in the taxonomy rather than the brochure? Show me the held-out score and the mistakes, not the accuracy on data it trained on. If it is classical, which features carry the decision, and who chose them? If it is an LLM doing a table's job, what did the table baseline score, and what does the difference cost per million rows?

# Train a Tiny Model 

> Training is not uploading knowledge. It is nudging a large pile of numbers until the model's next guess scores better, and a model small enough to train in seconds lets you watch every nudge.

Notebook companion: `train_tiny_model.ipynb` in the package repository's `notebooks/` folder. It runs on a laptop CPU in seconds at its defaults, or on a free Colab GPU if you prefer. This chapter narrates it; the notebook is the doing.

Everything before this part needed a model you could call and the Python in Appendix A. This part needs PyTorch (`pip install torch`, preinstalled on Colab) and introduces two ideas the earlier parts fenced out: loss and gradient descent, each explained in place without calculus. The builds are simplified teaching versions, in the open. Nothing here is how you would train for production, and the chapters say where the production road starts instead.

Misconception this chapter kills: "Training uploads knowledge into the model." Training adjusts weights so next-token guesses score better on examples. What looks like knowledge later is that adjustment, generalised or memorised, and this chapter shows you the difference on a graph.

The build: a character-level model of 38,874 parameters, trained on ten sentences about this book, sampled before and after training, then overtrained on purpose.

## The Concept First

Strip a language model to its training loop and four moves remain. Represent text as numbers, because arithmetic needs numbers: here, one integer per distinct character, the smallest workable tokenisation. Guess the next token everywhere in a batch of examples, with the current weights. Measure how wrong the guesses were with a loss, a single number that falls as guesses improve, computed here as cross-entropy, which you can read as average surprise at the true next character. Then nudge every weight a small step in the direction that would have reduced that loss on this batch, which is all gradient descent means here: follow the slope downhill, in small steps, many thousands of times.

Frontier training runs are those four moves at far larger scale, on trillions of tokens, with engineering beyond this book's scope. But scale changes the behaviour that emerges, not the identity of the moves. A model that has only ever done this, whose entire education is guessing the next character slightly less badly each step, is the same kind of object whose call you have been making since Chapter 1. When a large model answers from its training in Chapter 5's sense, this loop, on that text, is all the contact it ever had with the material.

## Understanding Through Real Life

Think of learning a piano piece by playing it through against a score you can check note by note. Each pass, you hear where your fingers expected one note and the score had another, and your hands adjust a little. Play one short piece five hundred times and two different things can happen. You might learn the piece so thoroughly that related music gets easier, the fingering patterns generalising. Or you might merely memorise this one sequence, brilliant at these forty bars and helpless at bar one of anything else. From outside, during practice, both feel like improvement. The test that separates them is a piece you have not practiced.

Training loss is your accuracy on the practiced piece. Validation loss, computed on held-out text the trainer never trains on, is the unpracticed piece. Watching only the first number is how overfitting goes unnoticed.

## The Build: Ten Sentences and a Sealed Test

Open the notebook and run it cell by cell the first time. The corpus is ten sentences about this book ("the model proposes and the code disposes" and its friends), small enough that you can audit every word the model could possibly learn. Eight sentences form the training text; two are held out whole as the sealed validation set, the same discipline the LocoLabo capstone enforces on its training data. The notebook lets you prove why that whole-sentence split matters: split repeated text at a character offset instead and the same sentences appear on both sides, after which validation loss flatters you by measuring memorisation and calling it learning. Leakage of that kind, in larger datasets, is behind a share of published AI results.

Before training, the notebook samples from the fresh model. Keep the output. In the run captured for this draft, seeded for reproducibility, the untrained model produced this, starting from the characters `the `:

the ifolhpydttyctri.jfemckylhcr.dpkxu.fsdscouotlf x deorxxxaoxdyilatyle

That is what near-random weights sound like: the alphabet available, no preferences worth the name. Then 600 steps of training, which took about four seconds on the machine that captured this run:

step    0  train 3.322  val 3.350
step  100  train 1.500  val 3.027
step  200  train 0.606  val 4.477
step  300  train 0.413  val 5.260
step  400  train 0.332  val 5.553
step  500  train 0.248  val 5.862
step  600  train 0.233  val 6.154

At step 0 the model is equally surprised by everything, training and held-out text alike. Training loss then falls without pause, as expected. Validation loss rises almost from the start. The model is not learning English or even these sentences' patterns in any general sense; it is memorising eight sentences with increasing fidelity, at the expense of the two it has never trained on. Sample it and the memorisation is audible: near-verbatim corpus sentences at low temperature, degrading gracefully as temperature rises and the sampler is allowed to choose less probable characters. Temperature, met here as a dial between conservative and adventurous sampling from the same weights, matters when hosted models expose it as a setting: it changes the choosing without changing the knowledge.

The notebook then overtrains deliberately, four times more steps, and the finishing figures in the captured run (training loss 0.153, validation 7.984) show the same pattern further along. Nothing malfunctioned: the optimiser did its job on the objective it was given, examples it was shown, and a corpus far too small to generalise from. Scale accounts for most of the difference between this small run and the models in Part I. The loop, the loss, the need for sealed evaluation, and the ease of lying to yourself with the wrong split did not vary with scale.

# Teach It a Dialect 

> Fine-tuning teaches a model how to answer here: the voice, the format, the habits. Facts still belong in evidence you can point at.

Notebook companion: `finetune_adapter_colab.ipynb` in the package repository's `notebooks/` folder, distilled from the LocoLabo capstone training notebook your author supervises. It needs a free Colab GPU. Budget tens of minutes at this chapter's scale, not the capstone's hours.

This chapter needs the notebook machinery from the previous one plus Unsloth in Colab, and it will happily consume an afternoon on data preparation alone. That is not overhead around the lesson. At this scale, data preparation is most of the lesson. Simplified throughout, as flagged: a production fine-tuning programme adds data governance, regression suites, and serving decisions this chapter only names.

Misconception this chapter kills: "Fine-tuning teaches the model our facts." An adapter mostly learns from relatively few examples how answers should sound and behave here. Whether it beats the base model at anything is an empirical question with a sealed test, and the honest answer is sometimes no.

The build: a LoRA adapter over Qwen3-4B teaching one plain-English answering dialect, exported to Ollama, then judged blind against its own base model.

## The Concept First

Almost nobody retrains a capable model from scratch to specialise it, for the arithmetic reason Chapter 16 made vivid: full training touches every weight, with the memory and compute to match. Fine-tuning starts from a pretrained base and continues the same next-token training on a small, deliberate dataset: examples of the behaviour you want more of, formatted as the conversations the model should learn to continue. LoRA, low-rank adaptation, goes one step thriftier. The base weights are frozen, and a small set of extra weights wired alongside key layers is the only thing trained: in the notebook's configuration, well under one percent of the total parameter count. At serving time the adapter can be merged back into the base to produce one ordinary model file, which is what the notebook exports for Ollama.

The proportion governs what this technique can and cannot do. A fraction of a percent of movable weights, trained on dozens to hundreds of examples, is enough to shift voice, format discipline, refusal habits, and which of the base model's existing knowledge gets foregrounded in a domain. It is a poor place to store a policy manual. Facts planted by fine-tuning arrive with no citation, go stale silently, and compete with everything else in the base, while Chapter 6's retrieval supplies facts at question time with sources attached. The division of labour is therefore: retrieval for what is true, system prompts for what is cheap to state, and an adapter only for behaviour that examples teach better than instructions do.

## Understanding Through Real Life

Think of accent coaching for an already fluent speaker joining a regional service desk. You do not reteach them the language. You give them fifty recorded calls that sound right for this desk: the greeting shape, the local terms, the calm way of saying no, and you drill until the habits are theirs under pressure. And you would not coach product prices into their accent, however many times they repeat them in training calls, because prices change next quarter and the information belongs on the screen in front of them, not in their muscle memory.

The measurement discipline matches too. You would not certify the coaching by replaying the practice calls. You would hold back calls the coach never used, have the newcomer handle them, and compare against how they sounded on day one, judged by the desk's own standards.

## The Build: Data First, Because Data Is the Build

## The Only Question That Matters: Did It Beat the Base?

Ask every sealed question of both models, the untouched base and your adapter, ideally with the answers shuffled and their sources hidden from whoever marks. Mark them against the criteria your dialect claims: plainness, brevity, format, whatever the adapter was for, using Chapter 11's judge as the tireless marker and your own reading of a sample as the moderation. Report both scores and read some actual answers, not only the aggregate, because a point gained in style while losing a fact is visible only at reading distance.

At this scale, unfashionable outcomes are common. The adapter may win on voice and lose on substance, which says your examples taught manner at the expense of content. It may match the base everywhere, which usually says a system prompt would have bought the same shift for almost nothing, and Chapter 2 should be tried first next time. Or it may lose, through too few examples, too many epochs, or a dialect the base already spoke. The capstone this notebook descends from states its position in its brief, and this chapter adopts it whole: a negative result with a rigorous explanation is a better piece of work than a flattering number nobody can defend. Publish the training log either way; the log template travels with the notebook materials for that reason.

## Extension: Learn from Preferences

Supervised fine-tuning imitates examples. Preference learning goes one step further and adjusts weights from comparisons: for the same prompt, this answer over that one. The simplest teachable form is DPO, direct preference optimisation, which consumes triples of prompt, chosen answer, and rejected answer and nudges likelihood toward the chosen style without a separate reward model to babysit. Your supply chain for pairs already exists in this book: generate two candidate answers per sealed-style prompt with your SFT model, rank them against your criteria (your marks first, the judge's second, per Chapter 11's order of trust), and file the winners and losers. The companion notebook's closing section sketches the additional cells; treat them as a second sitting, not a first run.

Beyond DPO sits online reinforcement learning proper, GRPO being the current teachable shape: sample several answers, score them with a reward, push weights toward the better-scoring behaviour, repeat. It earns its complexity only where the reward can be computed: arithmetic checked by Python, formats validated by a parser, code judged by its tests. At inference time, simple reward-guided search exists, and you built it in Chapter 10: the ratchet changes no weights. In weights, the simple on-ramp is preferences offline and verifiable rewards online; beyond that lies a research programme. Each step up this ladder is judged by the same sealed set, untouched by SFT, DPO, and every threshold conversation in between.

## Where a Demo Can Mislead You

"Fine-tuned on our data" is a claim about a process, not a result, and it demos beautifully because style is the easiest thing an adapter changes and the first thing an audience feels. Then ask the substitution question this chapter makes unavoidable: what here could retrieval or a system prompt not have done, cheaper and with citations? Look for answers that give behaviour examples and eval tables.

| `ModuleNotFoundError` | A package is not installed | Run the `pip install` step |
| `NameError` | A name was used before it existed | Spelling, or a missing import |
| `SyntaxError` or `IndentationError` | Python could not parse the file | The line it points at: quotes, colons, indentation |

Errors from the model call itself are different. As Chapter 1 explains, `get_response` returns them as strings beginning with ❌ or ⚠️ rather than stopping your program, and `handsonai doctor` is the first tool for those.

## A Worked Example Using Most of It

This script uses an import, a list of dictionaries, a loop, an f-string, and a function definition. It is the payload from Chapter 1, rebuilt from the pieces in this appendix, with no model involved:

text

{"model": "llama3", "messages": [{"role": "system", "content": "You are a helpful assistant."}, {"role": "user", "content": "What is my name?"}]}

# Model Access 

> Every setting this book needs, in one place: which server answers, which models fill which roles, what each chapter spends, and what to check when nothing answers.

The package resolves its configuration in a fixed order, weakest first: built-in defaults, then the config file at `~/.hands-on-ai/config.json`, then environment variables, which win over everything. `handsonai doctor` prints the resolved result and probes the server. `handsonai config` shows and edits the file layer. `handsonai models` lists what your server reports. When in doubt, run the doctor before touching code; it reads the same configuration your scripts will, in the same order.

## The Settings

| Variable | Role | Default |
|---|---|---|
| `HANDS_ON_AI_SERVER` | Chat, embedding, and vision server address | `http://localhost:11434` |
| `HANDS_ON_AI_API_KEY` | Key for every server above | unset (local servers ignore it) |
| `HANDS_ON_AI_MODEL` | Chat model | `llama3` |
| `HANDS_ON_AI_EMBEDDING_MODEL` | Retrieval embeddings, Chapter 6 | `nomic-embed-text` |
| `HANDS_ON_AI_VISION_MODEL` | Vision model, Chapter 13 | `moondream` |
| `HANDS_ON_AI_STT_SERVER` | Speech-to-text server, Chapter 14 | the main server |
| `HANDS_ON_AI_STT_MODEL` | Transcription model | `whisper-1` |
| `HANDS_ON_AI_TTS_SERVER` | Text-to-speech server, Chapter 14 | the main server |
| `HANDS_ON_AI_TTS_MODEL` | Speech model | `kokoro` |
| `HANDS_ON_AI_CACHE` | Response cache directory | unset, caching off |
| `HANDS_ON_AI_LOG` | Set to `debug` for verbose logging | unset |

Each row has a matching key in the config file (`server`, `api_key`, `model`, `embedding_model`, `vision_model`, `stt_server`, `stt_model`, `tts_server`, `tts_model`) for settings you want to survive terminal sessions. Environment variables still take precedence.

## The Free Local Path

Ollama covers chat, embeddings, and vision from one install at `http://localhost:11434` with no account and no key. The pulls this book needs:

```bash
ollama pull llama3           # chat (Parts I to IV)
ollama pull nomic-embed-text # retrieval (Chapter 6)
ollama pull moondream        # vision (Chapter 13)
Audio is the local exception. Transcription and speech typically come from a small separate server that speaks the same `/v1/audio/` dialect: speaches or whisper.cpp serving a Whisper model for speech-to-text, Kokoro or Piper for text-to-speech. Point `HANDS_ON_AI_STT_SERVER` and `HANDS_ON_AI_TTS_SERVER` at them and Chapter 14 works untouched. Local everything is the private, offline, per-call-free route; its costs are your hardware's limits on model size and patience, felt most in Parts III and V.

## Hosted Providers

Any service exposing the OpenAI-compatible chat and embeddings endpoints can drive most of the book through the three variables from Chapter 4. The package documentation carries worked examples; the shapes are uniform:

```bash
export HANDS_ON_AI_SERVER="https://api.openai.com"       # OpenAI
export HANDS_ON_AI_SERVER="https://openrouter.ai/api"    # OpenRouter
export HANDS_ON_AI_SERVER="https://api.groq.com/openai"  # Groq
export HANDS_ON_AI_API_KEY="your-key-here"
export HANDS_ON_AI_MODEL="the-provider's-model-name"

Audio and vision coverage varies by provider, so check the endpoints you need before a Part V weekend. Free tiers come and go and are deliberately not enumerated here; the package documentation and the providers are the live sources. One classroom pattern: one shared local or hosted server behind a key, the three variables issued to students, and the cache (below) warmed before the lesson so a network failure cannot fail thirty exercises at once.

## What Each Chapter Spends

Local calls cost time; hosted calls cost money per token. Either way, the shape of the spend per build is knowable in advance:

| Build | Calls, roughly |
|---|---|
| Part I scripts | 1 per line you run |
| `Conversation` | 1 per turn, over a resent transcript that grows |
| Indexing, Chapter 6 | 1 embedding call for all chunks, then 1 per question plus its embedding |
| One agent run | 1 per iteration, up to `max_iterations` |
| One judged loop iteration | 1 step call + 1 judge call |
| One ratchet proposal | 1 step call + 1 scoring call, plus 1 to score the start |
| One vision question | 1, carrying a large payload, on a slow clock |
| One voice turn | 1 transcription + 1 chat + 1 synthesis |

Budgets in the chapters (`max_iters`, `max_iterations`) are counted in iterations, not calls. Multiply before you fund a run.

## The Response Cache

Setting `HANDS_ON_AI_CACHE` to a directory turns on a plain-text reply cache for `get_response`: identical model, system prompt, and question return the stored answer without contacting a server, and with token usage reported as `None`. Warm it once for a classroom and reruns become reproducible, offline-capable, and free. Clear it by deleting the directory. Remember from Chapter 4 that it is also a folder of transcripts on disk, and that a model or prompt change does not invalidate old entries until the name inside the lookup changes. Note its scope: the cache sits in `get_response`, so direct `Conversation` turns and vision calls bypass it.

## Troubleshooting

| Symptom | Likely cause | First check |
|---|---|---|
| `❌ Error: Connection error.` | Server off, wrong address, blocked network | `handsonai doctor`; read the resolved server aloud |
| Error naming a model | Model never pulled, or name mismatch | `handsonai models`; compare with your settings exactly |
| 401 or 403 from a hosted server | Missing or wrong key | `HANDS_ON_AI_API_KEY` present in this terminal |
| Chat works, Chapter 6 fails | Embedding model missing | `ollama pull nomic-embed-text`, or the embedding setting |
| Chapter 13 fails, chat fine | Vision model missing or not vision-capable | `vision_model` setting; pull `moondream` |
| Chapter 14 fails, all else fine | Audio needs its own server | `STT`/`TTS` server variables actually set |
| Answers never change however you edit | The cache is serving stored replies | Unset `HANDS_ON_AI_CACHE` or delete the directory |
| Agent replies look unstructured | Small model in the text format | Let `format="auto"` choose, as Chapter 8 discussed |
| Everything worked yesterday | Settings were terminal-session exports | Put durable choices in `~/.hands-on-ai/config.json` |

One habit resolves most rows: run the doctor, read what it resolved, and argue with settings before arguing with scripts. The scripts in this book are short and seldom the problem; when they are, the error strings Part I taught you to read will usually say which line to look at.

## Three Capstones

Pick by your reason for reading. Each composes at least three parts of the book.

For a personal tool. A document assistant over your own notes: Chapter 6 retrieval over a folder you maintain, Chapter 3 conversation for follow-ups, Chapter 11 criteria checking that answers stayed inside the documents. # Going Deeper 

> A map, not a manual. For each module you outgrow, the grown-up neighbourhood to move into, and the idea from this book to carry through the door.

You will outgrow this package at a named moment: a budget it cannot express, a volume it cannot serve, an error it returns as a string where production needs a policy. Frameworks and services change quickly enough that this appendix names neighbourhoods and the current well-known residents, and trusts you to check who lives there when you arrive. The concepts are the durable part.

## The Call Itself (Part I)

Your next step is the providers' official SDKs, which add streaming, structured outputs, provider-native tool calling, and proper exceptions where this package returns error strings. If several providers must sit behind one interface in your own code, that is the job of routing layers such as LiteLLM, which generalise Chapter 4's three variables into a managed surface. Carry with you: the payload is still the truth; read what any SDK actually sends before trusting its abstractions, as Listing 1.2 taught you.

## Grounding (Part II)

Production retrieval adds vector stores, hybrid keyword-plus-vector search, metadata filtering, incremental reindexing, and evaluation sets for retrieval quality. LlamaIndex is the neighbourhood's best-known framework address, with LangChain's retrieval pieces and every vector database vendor nearby. Carry with you: it is still chunk, fetch, answer. The engineering is in chunking policy, freshness, and proving with scores and sampled answers that the fetch deserves the prompt built on it.

## Action (Part III)

Agent frameworks such as Pydantic AI and the SDKs' native agent tooling replace text-format parsing with validated function calling, add dependency injection for tools, retries with policy, and tracing as a first-class output. Carry with you: the model still only proposes. Your registry, your allowlists, and your worst-input discipline from Chapter 7 are the safety case, whatever the framework calls its decorators. Read Ship Python, Orchestrate AI in this series for this transition taken at professional length.

## Control (Part IV)

Workflow engines and durable-execution platforms add scheduling, parallelism, persistence across crashes, and human-task queues where this book had folders and a person at a bench. Evaluation matures into dataset-driven evals: fixed case sets, regression gates in CI, judge ensembles with measured agreement. Carry with you: stage outputs you can inspect, goals stated before loops run, and moderation records for every judge. A platform that hides any of the three removes evidence you need. Typed judgments grow up into structured-output modes in the official SDKs, schema-constrained decoding in local servers such as Ollama (verify the current `format` behaviour before relying on it), and dedicated System One services such as TypeSafe's Jev where calibrated probabilities are worth paying for.

## The Senses (Part V)

Vision production work adds image pipelines, detection and OCR specialists beside the general VLM, and thinking about resolution and cost per image. Voice production is its own stack, and Pipecat is the front door the package's final project points at: streaming transcription and synthesis, interruption handling, and the latency budget fought hop by hop. Carry with you: translators around a text core, and the consent and retention questions, which do not get simpler at scale.

## The Model Itself

One door remains if the black box itself is what you want opened. Andrej Karpathy's Zero to Hero series builds a small language model from first principles, at the cost of the mathematics Parts I to V promised to spare you: gradients, tensors, training loops. Its codebase line now runs from the deprecated nanoGPT to its successor nanochat, a full pretrain-to-chat pipeline kept deliberately hackable. Part VI opens this briefly, with toy training and a LoRA adapter; Karpathy covers it at full size. Nothing in Parts I to V requires either, and most builders of AI systems will never train a model.

Michael Borck is a software developer and educator working at the intersection of human expertise and artificial intelligence. He teaches applied AI and AI in business at Curtin University, and runs The Human Edge masterclasses through Curtin Executive Education.
